# T006：Job 与 Application Service

## 1. 任务目标

在 T002 领域模型、T003 持久化基础、T004 Repository 和 T005 Service/Unit of Work 基础上，实现 Job 与 Application 业务服务。

本任务负责：

- 手动保存结构化岗位并按 fingerprint 去重
- 将岗位加入候选人的待投池并创建 ApplicationRecord
- 防止同一 candidate/job 重复创建投递
- 使用确定性 Python 规则校验状态转换
- 状态变化时追加 ApplicationEvent
- 保证状态更新和事件写入处于同一事务
- 查询投递记录和事件 Timeline

本任务不得实现 T007 或任何后续功能。

不得实现：Streamlit、LangGraph、LLM 状态判断、邮件解析、Playwright、浏览器自动化、自动提交、JD Parser、Job Search、Job Normalizer、自动 fingerprint 算法、Match、Resume/答案生成以及 T007 后续功能。

## 4. 架构边界

- application service 不得导入 SQLAlchemy、ORM 或 Session。
- application service 不得调用 `commit()` 或 `rollback()`。
- Service 依赖 Repository Protocol 和 Unit of Work Protocol。
- SQLAlchemy Unit of Work 位于 infrastructure 层。
- 对外只返回领域对象、应用契约或 `Page[T]`。
- 不得向业务层暴露 ORM。
- 不得破坏 T005 的 Profile Unit of Work。

## 5. Job Service

至少提供等价能力：

```python
save_manual_job(job) -> JobPosting
get_job(job_id) -> JobPosting | None
list_jobs(limit=50, offset=0) -> Page[JobPosting]
```

岗位使用 fingerprint 作为业务唯一键：

- fingerprint 不存在时新增。
- fingerprint 已存在时调用 `JobRepository.upsert()`。
- upsert 可更新允许变化的信息。
- upsert 必须保留数据库中的 id、fingerprint 和 discovered_at。
- fingerprint 为空时必须在进入数据库前失败。
- Service 不得直接操作 SQL。
- 本任务不生成 fingerprint，也不解析或搜索 JD。

## 6. 待投池与投递创建

当前没有独立待投池表，因此采用以下语义：

- Job 单独存在只代表系统已保存岗位。
- 加入待投池时创建 ApplicationRecord。
- 初始状态固定为 `SHORTLISTED`。
- 同一 candidate/job 只能存在一条 ApplicationRecord。

至少提供等价能力：

```python
add_to_application_pool(request) -> ApplicationRecord
get_application(application_id) -> ApplicationRecord | None
list_applications(candidate_id, limit=50, offset=0) -> Page[ApplicationRecord]
list_application_events(application_id, limit=50, offset=0) -> Page[ApplicationEvent]
```

创建前必须确认 Candidate 和 Job 存在、application_url 合法；指定 resume_version_id 时应验证它存在且属于相同 Candidate。

相同 candidate/job 的重复请求不得创建第二条记录。完全相同的请求返回已有记录实现幂等；不可变信息冲突时抛出明确异常。不得把 IntegrityError 当作正常幂等流程。

初始 ApplicationRecord：

- `status=SHORTLISTED`
- `submitted_at=None`
- `last_updated_at` 为可注入 Clock 产生的 timezone-aware UTC 时间

同时追加：

```text
event_type = APPLICATION_CREATED
from_status = None
to_status = SHORTLISTED
source = 非空来源
occurred_at = 创建记录使用的 UTC 时间
```

ApplicationRecord 和初始事件必须位于同一事务。

## 7. 状态机

合法性由普通 Python 规则判断，不得调用 LLM。

```text
DISCOVERED
→ SHORTLISTED
→ PREPARING
→ READY_TO_APPLY
→ SUBMITTED
→ ONLINE_ASSESSMENT
→ INTERVIEW
→ OFFER
```

终止状态：`REJECTED`、`WITHDRAWN`、`CLOSED`。

实现独立、可单元测试的纯函数，例如：

```python
can_transition(from_status, to_status) -> bool
```

规则：

1. 正常状态可转换到状态链中任意更靠后的正常状态。
2. 正常状态可转换到任意终止状态。
3. 禁止回退到更早的正常状态。
4. 终止状态不能通过普通接口恢复。
5. 同状态请求幂等，不更新时间、不新增事件。
6. 非法转换必须在写数据库前失败。
7. 状态规则不得散落在 Repository、ORM 或 UI。

合法示例：SHORTLISTED→PREPARING、SHORTLISTED→READY_TO_APPLY、SUBMITTED→INTERVIEW、PREPARING→REJECTED、OFFER→CLOSED。

非法示例：PREPARING→SHORTLISTED、INTERVIEW→ONLINE_ASSESSMENT、REJECTED→INTERVIEW、WITHDRAWN→PREPARING。

终止状态恢复如果实现，必须使用独立显式接口，只允许人工来源，要求非空原因，并追加 `STATUS_RECOVERED` 事件。也可以本轮不开放恢复，但普通接口必须拒绝恢复并在报告中说明。

## 8. 时间语义

成功转换时保留 id、candidate_id、job_id，更新 status 和 last_updated_at。时间必须由可注入 Clock 产生并为 timezone-aware UTC；Clock 未前进时至少增加一微秒，保证单调。

submitted_at 规则：

- 第一次进入 SUBMITTED 时设置。
- 从提交前状态跨级进入 ONLINE_ASSESSMENT、INTERVIEW 或 OFFER 时也设置。
- 已有 submitted_at 后不得覆盖。
- 进入终止状态不会伪造 submitted_at。
- 未提交便终止时保持 None。

## 9. ApplicationEvent

每次真实状态变化必须追加：

```text
event_type = STATUS_CHANGED
from_status = 原状态
to_status = 新状态
source = 非空来源
details = 结构化字典
occurred_at = 状态变化使用的 UTC 时间
```

Event 为追加式审计记录，不得修改历史事件。非法转换和同状态幂等请求不产生 Event。details 不得包含密钥、Cookie、密码或认证数据。Timeline 按 occurred_at、id 稳定升序返回。

## 10. Unit of Work 与事务

可以新增 `JobApplicationUnitOfWork`，包含 candidates、jobs、applications，以及需要时的 resume_versions Repository；也可以安全扩展现有 UoW。

必须保证：

- 各 Repository 共享同一 Session。
- Service 不调用 commit/rollback。
- 正常退出由 UoW 提交，异常退出由 UoW 回滚。
- 状态已 flush 但 Event 写入失败时，状态更新不能保留。
- Application 已 flush 但初始 Event 失败时，Application 不能保留。

## 11. Repository 最小扩展

优先复用 T004 Repository。允许增加：

```python
get_by_candidate_and_job(candidate_id, job_id) -> ApplicationRecord | None
list_by_candidate(candidate_id, limit=50, offset=0) -> Page[ApplicationRecord]
```

若增加状态筛选，必须在 SQL 中先过滤，再 count、排序和分页；不得分页后内存过滤。Repository 只能 flush/refresh，不得 commit。

## 12. 异常策略

可新增 `InvalidApplicationTransitionError`、`ApplicationConflictError`、`InvalidManualRecoveryError`。

- Candidate、Job、Application 不存在时抛出明确异常。
- 非法状态转换使用专用异常。
- 重复 candidate/job 不泄漏 SQLAlchemy IntegrityError。
- application 层不得暴露 SQLAlchemy 异常。
- 错误信息不得包含敏感认证信息。

## 13. 测试要求

状态机单元测试至少覆盖：相邻前进、跨级前进、进入三个终止状态、拒绝回退、拒绝终止状态自动恢复、同状态幂等、所有 ApplicationStatus 被显式覆盖。

Job Service 集成测试至少覆盖：新增岗位、相同 fingerprint 去重、upsert 保留 id/fingerprint/discovered_at、更新可变字段、返回值不是 ORM。

Application Service 集成测试至少覆盖：

- Candidate/Job 存在时加入待投池，初始状态 SHORTLISTED。
- 同事务创建 APPLICATION_CREATED Event。
- Candidate 或 Job 不存在时失败。
- 同一 candidate/job 不重复，幂等请求不重复产生初始事件。
- 合法转换更新状态并追加 STATUS_CHANGED Event。
- 非法转换不更新状态且不产生 Event。
- 同状态请求不更新时间、不产生 Event。
- submitted_at 的首次设置、跨级设置和后续保留。
- last_updated_at 为 UTC aware 且单调增加。
- Timeline 稳定排序。
- Event 失败时状态整体回滚。
- 初始 Event 失败时 Application 整体回滚。
- Service 不调用 commit/rollback，不返回 ORM。

回归测试必须保证 T001～T005 测试继续通过，`python -m job_agent` 正常启动，测试仅使用临时数据库，不读写 `data/job_agent.db`。
