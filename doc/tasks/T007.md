# T007：Streamlit 基础 UI

## 1. 任务目标

在 T005 Profile Service 和 T006 Job/Application Service 基础上，实现本地单用户 Streamlit 基础界面，形成 V0.1 可操作的数据管理闭环。

本任务必须提供：

- Dashboard
- 个人资料
- 证据库
- 岗位录入
- 投递记录与 Timeline

页面刷新后，业务数据必须从 SQLite 重新读取并保持存在。UI 只通过应用 Service 使用业务能力，不直接操作 ORM、Session 或 SQL。

## 4. 总体架构

建议目录：

```text
job_agent/
└── ui/
    ├── app.py
    ├── bootstrap.py
    ├── navigation.py
    ├── errors.py
    ├── view_models.py
    └── pages/
        ├── dashboard.py
        ├── profile.py
        ├── evidence.py
        ├── jobs.py
        └── applications.py
```

可以根据实际工程调整，但必须遵守：

- 页面只能调用 Service 或专用应用查询服务。
- 页面不得导入 SQLAlchemy、ORM、Session 或 Repository 实现。
- 页面不得直接调用 LLM、LangGraph 或 Playwright。
- Streamlit Session State 只保存导航、表单草稿、确认状态等 UI 状态。
- Session State 不能作为 Profile、Evidence、Job、Application 或 Event 的事实存储。
- 业务数据必须以数据库为准，每次 rerun 后可重新查询。
- 模块导入不得连接数据库、创建表或启动 Streamlit。

## 5. 启动与依赖装配

在 `pyproject.toml` 增加 Streamlit 运行依赖，并提供文档化启动方式：

```powershell
python -m streamlit run job_agent/ui/app.py
```

要求：

- 保留现有 `python -m job_agent` 行为。
- UI 启动入口与 CLI 启动入口相互独立。
- 只有执行 UI `main()` 后才能创建 Engine、Session factory 和 Service。
- import `job_agent.ui` 或页面模块不得创建数据库连接或文件。
- 可以使用 `st.cache_resource` 缓存 Engine、Session factory 或 Service factory。
- 不得缓存业务查询结果作为事实来源。
- 每次写操作完成后重新从 Service 查询并展示数据库结果。
- 数据库未初始化或配置无效时显示安全错误，不显示完整堆栈。

## 6. Service 装配和查询边界

必须复用 T005/T006 已有：

- `ProfileService`
- `JobService`
- `ApplicationService`
- 对应 Unit of Work factory

Dashboard 若需要现有 Service 无法高效提供的聚合数据，可以增加最小的应用层查询契约，例如 `DashboardQueryService`、`DashboardSummary` 和 infrastructure 查询适配器。

新增查询能力必须满足：

- UI 仍然只调用 Service。
- application 层不依赖 SQLAlchemy。
- infrastructure 层负责 SQL 查询。
- 统计在数据库中完成，不得只读取第一页后在内存统计。
- 不修改数据库 Schema。
- 不修改 0001 migration。

## 7. 导航与全局布局

侧边栏至少包含：

```text
Dashboard

证据库
岗位录入
投递记录
```

要求：

- 页面标题和当前页面明确。
- 单用户模式下仍应明确当前 candidate_id。
- Candidate 不存在时给出创建入口，而不是页面崩溃。
- 空数据库必须显示空状态和下一步操作说明。
- 不得显示尚未实现功能的可点击假按钮。

## 8. Dashboard

展示当前数据库能够真实计算的内容：

- 本周新增岗位数
- 待审核 Evidence 数
- 待提交申请数
- 已投递数量
- ONLINE_ASSESSMENT 数量
- INTERVIEW 数量
- OFFER 数量
- 最近 ApplicationEvent
- 即将截止的岗位

建议定义：

- 待审核 Evidence：`UNVERIFIED`
- 待提交申请：`SHORTLISTED`、`PREPARING`、`READY_TO_APPLY`
- 已投递：`SUBMITTED`
- 即将截止：deadline 尚未过期并处于明确时间窗口，窗口必须在代码中集中定义和测试

当前尚未实现完整匹配服务，因此“高匹配岗位”不得伪造。可以明确显示为后续能力，或在没有可靠数据时省略。

Dashboard 规则：

- 所有数字来自数据库查询。
- 空数据库显示 0 和空状态。
- 不因某一模块查询失败导致整个页面不可用。
- 最近事件按 occurred_at 和 id 稳定排序。
- datetime 显示应明确时区或统一为本地展示规则。

## 9. 个人资料页面

必须支持：

- 创建 Candidate Profile
- 根据 candidate_id 查询 Profile
- 编辑基本信息
- 编辑教育、经历、技能和求职偏好
- 保存前预览变更
- 用户确认后调用 `ProfileService.create_profile()` 或 `update_profile()`
- 保存成功后重新读取数据库并展示

要求：

- 表单输入先转换为 Pydantic Schema，再调用 Service。
- Pydantic 校验错误转换为字段级或用户可理解提示。
- 未确认预览时不得写数据库。
- 取消预览不写数据库。
- created_at/updated_at 不允许用户伪造。
- 刷新页面后数据仍然存在。
- 嵌套列表可使用结构化表单、data editor 或经过严格 JSON/Pydantic 校验的编辑方式。

敏感信息：

- 手机号等敏感字段默认掩码展示。
- 敏感字段应与普通字段分区编辑。
- 密码、Cookie、Token、API Key 不得进入 Profile 表单或页面状态。
- 不新增当前领域模型不存在的敏感信息字段。

## 10. 证据库页面

必须支持：

- 按 candidate_id 查询 Evidence
- 查看内容、类别、来源和 verification
- 按验证状态筛选
- 明确区分全部审核数据与 VERIFIED 正式数据
- 对 UNVERIFIED Evidence 执行显式验证
- 验证成功后重新从数据库加载

要求：

- 正式证据视图只能使用 `list_verified_evidence()`。
- 审核视图使用 `list_evidence_for_review()`。
- 不得在 UI 中先分页再自行过滤 VERIFIED。
- 不得提供“关闭 VERIFIED 限制”的参数。
- 重复验证保持幂等。
- REJECTED 不得通过 verify 操作自动变为 VERIFIED。
- T005 未提供的编辑或拒绝能力不得通过 Repository 绕过；可以明确标注为后续功能。
- Evidence 来源路径不得暴露不必要的本机完整路径；默认显示安全名称或相对信息。

## 11. 岗位录入页面

必须支持手动录入当前 `JobPosting` 所需字段，包括：

- company
- title
- location
- url
- source
- raw_jd
- responsibilities
- requirements
- preferred_qualifications
- skills
- education/graduation/experience requirement
- deadline
- fingerprint

要求：

- T007 不自动生成 fingerprint。
- 页面明确提示 fingerprint 由用户或上游提供。
- 保存前完成 Pydantic 校验。
- 调用 `JobService.save_manual_job()`。
- 相同 fingerprint 保存后不产生重复岗位。
- 保存成功后显示数据库中的实际对象。
- 可以查看已保存岗位列表和详情。
- 可以选择 Candidate，将岗位加入待投池。
- 加入待投池必须调用 `ApplicationService.add_to_application_pool()`。
- 重复加入保持幂等，不重复创建 Application/Event。

## 12. 投递记录页面

必须支持：

- 按 candidate_id 查看 Application 列表
- 查看公司、岗位、URL、当前状态和更新时间
- 选择单条 Application 查看详情
- 查看 ApplicationEvent Timeline
- 手动更新到合法目标状态
- 更新成功后重新读取 Application 和 Timeline

状态更新要求：

- 可选目标必须来自 T006 状态规则，而不是 UI 自行复制一套不同规则。
- UI 不展示非法目标，Service 仍必须再次校验。
- 同状态不产生写入。
- 状态变化必须填写非空 source。
- details/reason 输入不得包含认证数据。
- 状态和 Event 同事务由 ApplicationService 保证。
- 终止状态恢复本轮不开放。
- Timeline 展示 event_type、from_status、to_status、source、occurred_at 和安全 details。
- 业务错误不能导致整个页面崩溃。

## 13. 错误处理与脱敏

建立统一 UI 错误边界，例如：

```python
UiError(code, message, trace_id)
```

要求：

- 用户看到简洁、可行动的中文错误信息。
- 页面显示 trace_id 以便排查。
- 页面不得展示 traceback、SQL、连接字符串、绝对认证文件路径或原始底层异常。
- 服务器日志可以记录异常链，但必须脱敏。
- 密钥、Token、Cookie、Authorization、密码不得显示或写入 Session State。
- 一个组件失败时，其他页面和导航仍可使用。
- 预期业务异常与未知异常采用不同的安全提示。
- 不得直接把 `str(exc)` 无条件展示给用户。

## 14. 页面状态

对于本任务中的同步操作，至少明确处理：

- `idle`
- `running`
- `succeeded`
- `failed`

`waiting_for_human` 和 `cancelled` 可保留为后续工作流状态，本轮不得伪造 LangGraph 运行。

按钮操作期间应有 spinner 或明确运行提示；成功后显示确认信息；失败后显示安全错误。

不得使用 `data/job_agent.db`。

- 不连接数据库

- 不启动服务器

Streamlit 启动验证必须设置测试端口并在有限时间内终止，不能在自动测试中永久阻塞。
