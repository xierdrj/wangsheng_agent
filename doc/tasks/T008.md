## 1. 任务目标

基于 T001～T007 已有领域契约、数据库、Repository、应用 Service 和 Streamlit UI，完成 V0.1 核心业务闭环的跨层集成验收、必要缺陷修正和文档收口。

## 3. 当前系统基线

### 3.1 现有公开接口

- Profile：`ProfileService.create_profile(profile)`、`get_profile(candidate_id)`、`add_evidence(evidence)`、`verify_evidence(evidence_id)`、`list_evidence_for_review(candidate_id, ...)`、`list_verified_evidence(candidate_id, ...)`、`list_evidence_by_verification(candidate_id, verification, ...)`、`import_structured(payload)`。
- Job：`JobService.save_manual_job(job)`、`get_job(job_id)`、`list_jobs(limit=50, offset=0)`。保存复用 `JobRepository.upsert()`，以调用方提供的 `fingerprint` 为唯一键。
- Application：`ApplicationService.add_to_application_pool(request)`、`get_application(application_id)`、`list_applications(candidate_id, ...)`、`list_application_events(application_id, ...)`、`transition_status(request)`。
- Application 请求契约：`AddToApplicationPoolRequest`、`ApplicationTransitionRequest`。
- 确定性状态规则：`job_agent.application.rules.can_transition` 和 `is_submitted_or_later`。
- Dashboard：`DashboardQueryService.get_summary(candidate_id)` 返回 `DashboardSummary`，含 `jobs_added_this_week`、`evidence_pending_review`、`applications_pending_submission`、`applications_submitted`、`online_assessments`、`interviews`、`offers`、`recent_events`、`upcoming_jobs`。
- UI 装配：`job_agent.ui.bootstrap.create_service_bundle(settings)`，返回包含 `profile`、`jobs`、`applications`、`dashboard` 服务的 `ServiceBundle`。
- 数据库：`create_engine_from_url` / `create_engine_from_settings`、`create_session_factory`、`initialize_database`、`SqlAlchemyProfileUnitOfWork`、`SqlAlchemyJobApplicationUnitOfWork`、`SqlAlchemyDashboardReader`。

不得在 T008 中创建同名替代 Service、Repository 方法或 DTO。规格外需要的新业务接口须停止并报告。

### 3.2 真实枚举与状态路径

`ApplicationStatus` 当前包含：

```text
DISCOVERED, SHORTLISTED, PREPARING, READY_TO_APPLY,
SUBMITTED, ONLINE_ASSESSMENT, INTERVIEW, OFFER,
REJECTED, WITHDRAWN, CLOSED
```

普通流程允许正常状态链向任意更后状态推进；正常状态也可进入任一终止状态。禁止正常状态回退，终止状态不能通过普通规则恢复。同状态由 `can_transition` 判为允许，但 `ApplicationService.transition_status` 会原样返回当前记录，不更新时间、不新增事件。

本任务主验收路径使用 `SHORTLISTED → PREPARING → READY_TO_APPLY`。该路径由待投池创建出的 `SHORTLISTED` 起步，且每步均由现有规则允许；不得在 UI 或测试中另写状态矩阵。

### 3.3 现有测试覆盖基线

当前测试已覆盖 T003 数据库/迁移、T004 Repository/分页/事务、T005 Profile/Evidence、T006 状态机与 Application/Event 原子性、T007 Dashboard/AppTest/ServiceBundle 持久化。实施前应先运行完整测试并读取失败详情；T008 只补现有测试未覆盖的跨任务闭环，不重复已有细粒度测试。

### 3.4 文档差异处理

- 领域设计文档描述了确定性 fingerprint 的生成策略，但当前 T006/T007 明确只接收调用方提供的 fingerprint，且禁止自动生成。T008 按当前真实接口验证去重，不实现生成算法。
- API/UI 设计文档列有建议性质的旧 Service 方法名；T008 以本节列出的当前代码公开方法为准，不为贴合旧示例增加别名或新业务接口。
- 领域文档及当前枚举包含 `EvidenceVerification.REJECTED`，而 T005 早期任务描述存在枚举范围不一致。T008 保留实际领域枚举和 T005 当前行为，不增删状态；正式查询仍只允许 VERIFIED。

## 6. V0.1 端到端验收场景

在单个 `tests/e2e/test_v01_workflow.py` 主场景中执行以下顺序，使用 Pydantic 领域对象和现有公开 Service 接口：

1. 使用固定、timezone-aware UTC 时间 Clock 建立空的临时 SQLite 数据库和真实 ServiceBundle；确认候选人、Evidence、Job、Application、Event 初始数量为 0。
2. 用 `ProfileService.create_profile(CandidateProfile(...))` 创建 Candidate Profile，断言返回 `CandidateProfile`，ID 和基本字段正确。
3. 用 `ProfileService.add_evidence(ResumeEvidence(...))` 新增 Evidence，省略 verification 或显式传 `UNVERIFIED`；断言落库后仍为 `UNVERIFIED`。
4. 验证调用 `list_verified_evidence(candidate_id)` 尚不返回该 Evidence；使用显式 `verify_evidence(evidence_id)` 后再次调用正式查询，确认该 Evidence 出现且 verification 为 `VERIFIED`。
5. 用 `JobService.save_manual_job(JobPosting(...))` 保存结构化岗位，传入测试自行指定的非空 fingerprint 和相对固定 Clock 的未来 deadline；不得计算或声称自动生成 fingerprint。
6. 再次保存业务内容可变、但 fingerprint 相同且输入 ID 不同的 `JobPosting`；断言仍只有一条 Job，返回/查询结果保留数据库原始 `id`、`fingerprint`、`discovered_at`，并符合现有 upsert 对可变字段的行为。
7. 构造 `AddToApplicationPoolRequest`，调用 `ApplicationService.add_to_application_pool`；断言 Application 状态为 `SHORTLISTED`、`submitted_at is None`，并产生且只产生一条 `APPLICATION_CREATED` 初始 Event。
8. 调用 `transition_status` 依次将该 Application 推进为 `PREPARING`、`READY_TO_APPLY`。每个请求提供非空 source；第二次请求可带普通结构化 `details`。断言两个目标均通过 `can_transition`，状态按请求更新。
9. 使用原始相同的 `AddToApplicationPoolRequest` 再次调用 `add_to_application_pool`；断言返回数据库中的当前 Application（仍为 `READY_TO_APPLY`），candidate/job 组合只有一个 Application，且重复请求没有创建第二条 `APPLICATION_CREATED`。
10. 调用 `get_application` 和 `list_application_events`；断言最终状态为 `READY_TO_APPLY`，初始 Event 的 `from_status is None`、`to_status is SHORTLISTED`，两个 `STATUS_CHANGED` Event 各自准确记录前后状态。Clock 不前进时，Service 应按 T006 规则保证每次真实变化的 `last_updated_at` 严格增加，且 Event `occurred_at` 等于该次状态更新时间。
11. 检查 Timeline 的全部事件数、类型、状态和顺序。Timeline 使用仓库现有稳定排序（`occurred_at`、`id` 升序）；若多个 Event 时间相同，增加同值情况下按 `id` 稳定排序的断言，不依赖插入顺序或数据库偶然顺序。
12. 调用 `DashboardQueryService.get_summary(candidate_id)`，断言真实数据库聚合值：本周新增岗位 1、待审核 Evidence 0（该 Evidence 已验证）、待提交申请 1（最终 `READY_TO_APPLY`）、已投递/在线测评/面试/Offer 均为 0；最近事件至少包含该 Application 的 Event，未来 14 天截止岗位包含该 Job。不得从 Repository 分页结果自行内存计算 Dashboard 指标。
13. 正常关闭第一组 ServiceBundle/Engine；以相同 SQLite URL、重新创建的 Engine、Session factory、Unit of Work、查询 Reader 和 ServiceBundle 验证 Profile、VERIFIED Evidence、单条 Job、Application 最终状态、时间字段、Event 数量和 Dashboard 指标仍与关闭前一致。

为了使 Dashboard 时间断言确定：测试 helper 可将固定 Clock 注入真实 `ProfileService`、`ApplicationService` 和 `DashboardQueryService`，并将同一固定 aware UTC 时间作为 JobPosting 的 `discovered_at`；deadline 使用相对该 Clock 的固定偏移。测试 helper 必须装配真实 Repository/UoW/Reader，不可 Mock 数据层或直接写 ORM。也可以在保留该固定时钟约束的前提下通过真实 `create_service_bundle(Settings(...))` 完成持久化重建，并对该 bundle 额外做不依赖精确时间的 smoke 验证。

## 9. Job 去重和持久化验收要求

- 用 `JobPosting` 构造已经结构化的岗位，满足实际必填字段和 aware datetime 校验。
- 仅调用 `JobService.save_manual_job` 保存/去重，不调用 ORM 或 `JobRepository.upsert` 作为业务入口。
- fingerprint 为测试显式提供的非空稳定字符串；不得在 T008 实现 fingerprint 算法。
- 同 fingerprint、不同请求 ID 的重复保存不能新增第二行；断言列表 `total == 1` 或使用只读 Inspector/SQL 检查。
- 断言 upsert 返回领域 `JobPosting` 并保留原 ID、fingerprint、discovered_at；可变字段行为必须符合 T006/T004 当前规则。
- Dashboard 的本周岗位数量来自真实数据库查询，断言值基于当前 Workflow 写入，不得从第一页数据或内存列表计算。

## 10. Application 与状态转换验收要求

- 使用 `AddToApplicationPoolRequest`，由 `ApplicationService.add_to_application_pool` 创建待投池记录。
- 创建时 Candidate 和 Job 均由前序 Service 操作存在；初始状态必须为 `SHORTLISTED`，`submitted_at` 必须为 `None`。
- 主路径使用 `SHORTLISTED → PREPARING → READY_TO_APPLY`；每步可先用现有 `can_transition` 断言为合法，再调用 Service。不得在测试中定义另一份状态规则。
- 每个状态转换 source 使用非空值；details 只使用非敏感结构化字典。
- Service 的最终状态、`last_updated_at`、`submitted_at` 通过 `get_application` 或返回领域对象验证。
- 同状态无副作用、非法转换、全部枚举规则及 submitted_at 其他分支已由 T006 单测/集成测试覆盖；T008 不重复造一份状态矩阵，但必须运行这些回归测试。
- 若端到端断言涉及 submitted_at，应按当前路径在进入 `SUBMITTED` 或更后正常状态时首次设置；当前建议主路径停留在 `READY_TO_APPLY`，因此预期仍为 `None`。

## 11. ApplicationEvent 与 Timeline 验收要求

- Application 创建必须同事务产生一条 `APPLICATION_CREATED`，其 `from_status is None`、`to_status is SHORTLISTED`、source 与请求一致。
- 两次真实状态变化各产生一条 `STATUS_CHANGED`，事件的 from/to 与变化前后状态一致。
- 每次状态 Event 的 `occurred_at` 应等于同一次状态更新采用的 UTC 时间；时钟未前进时 `last_updated_at` 仍严格单调增加。
- 重复加入待投池不能新增 `APPLICATION_CREATED`；同状态转换不新增 `STATUS_CHANGED`。
- 使用 `ApplicationService.list_application_events(application_id)` 查询 Timeline，断言稳定的 `occurred_at`、`id` 顺序。
- Event 是只追加的历史记录；T008 不增加 Event 编辑或删除业务入口。
- 现有 T006 测试已覆盖 Event 写入失败回滚；T008 全量回归必须实际运行该测试，不通过伪造成功的 Mock 替代。

## 12. Dashboard 指标验收要求

- Dashboard 所有指标、事件和截止岗位来自真实 Reader/数据库聚合；不得 Mock Summary，也不得分页后自行聚合。
- Candidate 缺失、空数据库、周边界、截止边界和所有状态分组已由 T007 专项测试承担；T008 运行这些回归并只补集成链路发现的缺口。

## 14. 幂等性要求

- 重复保存相同 fingerprint 的 Job 只保留一条业务记录，并保留原始业务 ID 和不可变时间字段。
- 相同 `candidate_id + job_id` 重复加入待投池，只保留同一个 Application。
- 完全相同的待投池请求重复执行应返回数据库中当前 Application（即使状态已推进），不能将状态重置回 `SHORTLISTED`。
