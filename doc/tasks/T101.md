# T101：JD Parser Port 与 Fake 实现

## 1. 任务目标

T101 为 V0.2 岗位发现链路建立可替换、可测试的 JD 解析边界：

- 在 application/ports 定义唯一的 JD Parser Port；
- 在 application/contracts 定义原始输入和结构化中间输出契约；
- 用 Pydantic 校验输入和输出，拒绝未知字段与无效 URL；
- 提供确定性的 Fake Parser 和脱敏 Fixture；
- 用单元测试固定 Port、契约、Fixture、确定性和错误行为；
- 为 T102 的真实 LLM Parser 提供不绑定供应商 SDK 的稳定边界。

本任务只建立解析边界，不把解析结果写入岗位数据库，也不改变 T002～T008 的公开业务行为。

## 3. 当前系统基线

当前 JobPosting 的真实字段包括：id、可选 external_job_id、company、title、可选 location、url、source、raw_jd、responsibilities、requirements、preferred_qualifications、skills、可选教育/毕业/经验要求、可选 deadline、fingerprint 和 discovered_at。

其中 id、fingerprint、discovered_at 是持久化生命周期字段，url、source 是已保存岗位的来源字段。T101 的解析输出不得假定这些字段已经存在，也不得调用 JobService 或 JobRepository。

现有应用层 Port 使用标准库 Protocol，Repository/UoW 采用同步调用；因此 T101 采用同步解析方法。当前没有真实外部调用所需的异步运行时或重试抽象，不在本任务引入异步接口和第二套 Parser 接口。

## 4. 术语定义

- 原始 JD：调用方提供的岗位描述文本，不代表已验证或已标准化的岗位事实。
- Parser 输入：原始 JD 及可选来源元数据的 Pydantic 请求对象。
- ParsedJD：解析阶段的中间结构化结果；允许字段缺失，不能替代最终 JobPosting。
- 硬性要求：原文明确要求满足、否则通常不符合的条件。
- 优先条件：原文明确表述为优先、加分或 preferred 的条件，不能升级为硬性要求。
- 歧义项：无法在不猜测的情况下确定含义、范围或是否为硬性条件的原文片段或说明。
- Fixture：包含脱敏原始输入和期望 ParsedJD 的固定测试样例。

## 5. 实现范围

只允许新增与以下内容直接相关的代码和测试：

- JDParseRequest、JDRequirement、ParsedJD、JDParserFixture 等契约；
- JDParser Protocol；
- FakeJDParser 及必要的 Fake 异常；
- 三份以上虚构 JD Fixture（完整、缺失字段、硬性/优先条件可区分）；
- Port/契约/Fake 的单元测试；
- 必要的稳定导出路径。

Fake 的输入映射、Fixture 加载和返回对象都必须经过 Pydantic 校验。测试应使用真实 Port/契约，不以字典或 ORM 对象作为 Parser 公共返回值。

## 6. 明确不在范围内的内容

- 真实 LLM、模型供应商 SDK、网络请求、Prompt 调优或 API Key 读取；
- 岗位搜索、网页抓取、Job Normalizer；
- 自动 fingerprint、Hard Filter、Evidence Retriever、Semantic Matcher；
- LangGraph、Playwright、Streamlit 新页面或 FastAPI；
- 数据库 Schema、ORM、Repository、Service、Alembic migration；

- 将解析结果自动写入 data/job_agent.db 或默认数据库。

## 8. Parser 输入契约

建议在 job_agent.application.contracts.jd_parser 定义：

~~~python
class JDParseRequest(DomainModel):
    raw_jd: str = Field(min_length=1)
    source_url: str | None = None
    source_name: str | None = None
    external_job_id: str | None = None
    trace_id: str | None = None
~~~

规则：

- `raw_jd` 为空字符串或 `raw_jd.strip()` 为空时，在构造/校验 `JDParseRequest` 时产生 Pydantic `ValidationError`；不得进入 Fake 或未来模型调用。实现应通过字段/模型校验器表达该约束，不定义额外的空白输入运行时异常；
- 原文不得由 Fake 擅自补全、改写或拼接；若输出保留 raw_jd，不得改变其内容；
- `source_url` 非空时复用现有 HTTP(S) 约束，只接受带主机的 `http` 或 `https`；非法 URL 在构造/校验 `JDParseRequest` 时产生 Pydantic `ValidationError`，拒绝 `file`、`javascript` 和裸路径；
- 未声明字段在构造/校验 `JDParseRequest` 时产生 Pydantic `ValidationError`；
- source_name、external_job_id 是可选来源元数据，不承担数据库 ID 或 fingerprint 语义；空白值规则必须由测试固定；
- `trace_id` 仅是可选调用关联信息，允许为空，不得承载密钥、Cookie、密码或原文；调用方负责关联请求和结果。本任务中它不进入 `ParsedJD`，不持久化，也不成为业务事实；不新增第二套响应包装对象；
- 输入契约只依赖标准库、Pydantic 和领域校验函数，不依赖 SQLAlchemy、Session、ORM、Streamlit 或模型 SDK。

请求校验错误的消息不得包含原文全文、文件绝对路径或底层 JSON 异常。`JDParser.parse()` 只接收已经校验成功的 `JDParseRequest`。

## 9. Parser 输出契约

输出必须是 Pydantic ParsedJD，不是 dict、ORM 或 JobPosting。推荐结构如下，实施时可在不改变语义的前提下调整名称，但必须保持单一稳定契约：

~~~python
class JDRequirement(DomainModel):
    text: str = Field(min_length=1)
    category: Literal[
        "skill", "education", "experience", "graduation",
        "language", "location", "other"
    ]

class ParsedJD(DomainModel):
    raw_jd: str = Field(min_length=1)
    source_url: str | None = None
    source_name: str | None = None
    external_job_id: str | None = None
    title: str | None = None
    company: str | None = None
    location: str | None = None
    job_type: str | None = None
    responsibilities: list[str] = Field(default_factory=list)
    hard_requirements: list[JDRequirement] = Field(default_factory=list)
    preferred_qualifications: list[JDRequirement] = Field(default_factory=list)
    skills: list[str] = Field(default_factory=list)
    education_requirement: str | None = None
    experience_requirement: str | None = None
    graduation_requirement: str | None = None
    languages: list[str] = Field(default_factory=list)
    deadline: datetime | None = None
    deadline_text: str | None = None
    ambiguous_items: list[str] = Field(default_factory=list)
~~~

规则：

- 所有列表用 default_factory，模型默认 extra="forbid"；
- title、company、location、job_type 和各要求字段允许缺失，使用 None 或空列表，不得用“未知”伪造事实；
- responsibilities 不混入技能或候选人事实；
- hard_requirements 与 preferred_qualifications 独立。“优先、加分、preferred、nice to have”等只能进入 preferred；无法确定时进入 ambiguous_items；
- skills 只列原文明确出现的技能，不做自动同义词扩展；
- 学历、经验、毕业年份、语言没有信息时使用 None/空列表，不猜测；
- deadline 只有在原文和上下文足以确定带时区时间时才设置。缺少时区或语义不确定时保留 deadline_text 并记录 ambiguous_items，不采用机器本地时区；
- raw_jd 若保留必须与输入原文一致，未识别段落不得删除；
- `trace_id` 不属于 `ParsedJD` 输出；调用方通过输入请求自身关联请求和结果，Parser 不返回第二层包装对象。

## 10. 与 JobPosting 的边界

ParsedJD 是解析中间结果，JobPosting 是具备持久化和岗位生命周期语义的领域对象，二者不得互相冒充：

| 事项 | ParsedJD | JobPosting |
|---|---|---|
| 解析结果 | 允许缺失，保留歧义 | 应满足保存岗位所需字段 |
| id | 不生成 | 由应用流程提供 |
| url/source | 仅保存可选来源元数据 | 保存岗位来源 |
| fingerprint | 不计算 | 由后续 T104/调用方提供 |
| discovered_at | 不生成 | 由发现/保存流程提供 |
| 数据库写入 | T101 不写入 | 由 JobService/Repository 负责 |
| 标准化 | 不做最终规范化 | 后续 Normalizer 决定 |

T101 不得为了复用 JobPosting 而填充虚构 id、fingerprint、discovered_at、公司、标题或 URL。T104 应显式把 ParsedJD 转换为标准化岗位，再由既有 JobService 决定保存策略。

## 11. JD Parser Port

在 job_agent.application.ports.jd_parser 定义唯一正式 Port：

~~~python
class JDParser(Protocol):
    def parse(self, request: JDParseRequest) -> ParsedJD: ...
~~~

要求：

- 方法同步，因为当前 application services、Repository/UoW 和测试均为同步风格；
- 参数和返回值只能是标准库类型、Pydantic 契约或领域值对象，不得出现 SQLAlchemy、Session、ORM、Streamlit、LangGraph 或供应商 SDK 类型；
- Port 不负责事务、数据库写入、fingerprint、状态转换、搜索、重试或供应商配置；
- 只定义一个 parse 用途，不再并列定义 parse_text、extract 等重叠接口；
- `parse()` 接收已经通过 Pydantic 校验的请求；Parser 执行失败和 Fake 未命中必须通过项目级异常暴露，不能静默返回空岗位。

应从 application.ports 和必要的 application.contracts 稳定导出，但不得破坏 T001～T008 的已有导出。

## 12. Fake Parser 行为

建议在 job_agent.infrastructure.fakes.jd_parser 实现 FakeJDParser，并让结构性调用验证成立。

规则：

1. 构造时显式接收已加载且已校验的 Mapping[str, ParsedJD] 或 Mapping[str, JDParserFixture]；不在模块导入时扫描目录、读取文件、连接数据库或访问网络。
2. 内部只采用一种规范键策略：`external_job_id` 非空时使用其精确值；缺少 `external_job_id` 时使用完整 `raw_jd` 原文 UTF-8 字节的稳定 SHA-256 摘要。Fixture 映射和请求查找都使用该规范键；不得在同一实现中再提供原文键、关键词键、模糊相似度或默认 Fixture 回退。
3. 未配置输入抛 FakeJDParserNotConfiguredError（继承 JDParserError），不得在异常中包含完整原文、绝对路径或 JSONDecodeError。
4. 相同输入始终返回相同语义结果；Fake 不调用网络、不读取 API Key、不读取 .env，也不依赖当前工作目录。
5. 每次 parse 返回深拷贝/安全副本；调用方修改一次结果后，再次解析不得被污染。
6. 返回前再次通过 ParsedJD.model_validate 校验，非法 Fixture 在构造或首次调用时明确失败。
7. Fake 不映射 JobPosting，不生成 fingerprint、ID、截止时间或候选人事实。

Fixture 的 `expected.raw_jd`、`expected.source_url`、`expected.source_name` 和 `expected.external_job_id` 必须与 `input` 对应字段一致；不一致在 Fixture 构造/校验阶段失败。若调用方使用同一合法 `external_job_id` 提供不同但仍合法的来源元数据，Fake 返回结果以当前请求元数据为准，但始终保持 `raw_jd` 与请求完全一致。

## 13. Fixture 设计

建议在 tests/fixtures/jd_parser/保存 JSON，每份文件同时包含 input 和 expected，并有 fixture_id：

~~~json
{
  "fixture_id": "complete-cn",
  "input": {
    "raw_jd": "虚构公司……",
    "source_url": "https://jobs.example.com/fake/complete-cn",
    "source_name": "fixture-board",
    "external_job_id": "fixture-complete-cn"
  },
  "expected": {
    "raw_jd": "虚构公司……",
    "title": "算法工程师",
    "company": "虚构科技有限公司",
    "hard_requirements": [],
    "preferred_qualifications": []
  }
}
~~~

至少提供：

- 完整中文 JD：包含公司、标题、地点、职责、硬性技能、学历/经验和语言等多个可观察字段；
- 字段缺失 JD：明确缺少公司、地点或截止日期中的至少一项，期望使用 None/空列表，不填写猜测；
- 硬性/优先区分 JD：同时出现明确硬性条件和“优先/加分”条件，期望验证两者没有串位。

Fixture 使用虚构公司、岗位、网址和文本，不包含真实个人信息、简历、密钥、Cookie、Token 或真实招聘数据。加载由测试显式传入文件路径并在运行时完成；不能在 import 时读取 Fixture，也不能把绝对路径写入异常、日志或断言文本。JSON 日期必须通过 Pydantic 校验并明确时区规则。

## 14. 异常设计

建议异常层次：

~~~python
class JDParserError(ValueError):
    """JD Parser 执行阶段错误。"""

class FakeJDParserNotConfiguredError(JDParserError):
    """Fake 没有为当前输入配置 Fixture。"""
~~~

`JDParserError` 只用于 Parser 执行阶段错误；`FakeJDParserNotConfiguredError` 继承它，用于合法请求没有对应 Fake 配置。空字符串、纯空白 `raw_jd`、非法 URL 和未知字段均在构造/校验 `JDParseRequest` 时产生 Pydantic `ValidationError`，不由 `JDParser.parse()` 或 Fake 重新定义。不能泄漏 JSONDecodeError、绝对路径或底层供应商异常。不得捕获并吞掉异常。

空白输入、非法 URL、未知字段、Fixture 未命中均必须有单独可断言的失败测试。错误消息只能描述字段或错误代码，不回显完整 JD 或密钥。

## 15. 确定性与可变状态隔离

- 相同输入和相同 Fixture 映射必须产生相同 Pydantic 值；不得依赖当前时间、随机数、网络、环境变量或测试执行顺序；
- Fixture 映射在 Fake 构造后应复制或视为不可变；修改返回对象列表、嵌套对象不能污染下一次结果；
- 测试先解析两次再修改第一次结果，随后断言第二次仍等于原期望；
- 不使用可变默认值，列表字段必须用 Field(default_factory=list)；
- 不要求 frozen，但必须通过深拷贝和契约边界防止共享状态。

## 16. 架构依赖规则

- application.contracts、application.ports 只依赖标准库、Pydantic、domain Schema 和应用契约；
- 上述模块不得导入 SQLAlchemy、Alembic、Streamlit、ORM、Session、Playwright、LangGraph 或模型 SDK；
- infrastructure.fakes 可以依赖 application contracts/ports，但不得反向污染 application/domain；
- domain 不得依赖 Parser、Fake、数据库或模型 SDK；
- Fake 不得读取 API Key、.env，不得访问网络；
- import 阶段不得读取 Fixture、创建数据库文件、连接数据库或启动服务；
- 不修改 migrations/versions/0001_initial_persistence.py，不新增 Schema 或 migration；
- 不改变 JobPosting、T004/T005/T006/T007 的公共语义，不在 T101 增加 Job 保存 Service。

## 18. 安全与隐私要求

- 不读取、输出或提交 .env 中的密钥；Fake 不需要 API Key；
- Fixture 只能使用虚构公司、岗位、URL 和合成文本，不放真实简历、手机号、邮箱、Cookie、Token、Authorization 或密码；
- 原始 JD 可能包含招聘方或个人信息，错误、日志和测试失败信息不得回显全文；
- T101 没有真实模型，不记录 Prompt/Response，不新增供应商、模型名称或密钥字段；
- URL 校验沿用现有 HTTP(S) 规则；不在 Parser 中执行 URL 请求；
- 不生成、写入或提交数据库、缓存、日志、截图或个人文件。

## 19. Schema 和 migration 要求

T101 只增加应用层契约和测试支持，不改变现有 ORM Schema、数据库表或 Alembic revision。禁止修改 migrations/versions/0001_initial_persistence.py，原则上不得新增 migration。

解析结果不自动保存到数据库。若后续发现 JobPosting 无法承载某字段，应由 T104/独立任务提出 Schema 变更，不能在 T101 中偷偷扩表或修改既有领域模型。
