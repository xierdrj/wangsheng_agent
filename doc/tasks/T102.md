# T102：JD Parser LLM 实现

## 1. 任务目标

在 T101 稳定的同步 `JDParser` Port 上新增一个可显式启用的真实 LLM 适配器。适配器负责把原始 JD 转成既有 `ParsedJD` 中间契约，可靠区分硬性要求与优先条件、保留缺失信息，并对所有模型输出执行严格 Pydantic 校验。

本任务是 T101 Fake 的增量实现，不替换或改变 Fake，不持久化解析结果，不改变 JobPosting、Service、Repository 或数据库结构。真实网络只能由显式配置和显式启用触发；默认测试和默认启动路径保持离线。

## 2. 前置依赖

- T001～T008 与 T101 已完成；当前 T101 基线在 `doc/AI_HANDOFF.md` 记录为完整测试 172 passed。
- T101 的 `JDParseRequest`、`JDRequirement`、`ParsedJD`、`JDParserFixture`、`JDParser`、`JDParserError` 和 `FakeJDParser` 是本任务的既有公共契约。
- 实施前重新检查实际分支、工作区、公开导出和测试结果。不得依赖本规格之外的新 Parser Port 或另造一套 ParsedJD。
- T101 的 raw JD 原文、来源元数据和 trace_id 规则保持不变。T101 Fixture 与 Fake 必须继续通过原有测试。

## 3. 当前基线

- Python 3.11+；application Service、Repository、Unit of Work 与 T101 Parser Port 均为同步风格。
- 配置实际位于 `job_agent/config/settings.py`，稳定入口为 `job_agent.config.Settings` / `ConfigurationError`；没有 `job_agent/config.py`。
- `Settings.from_env()` 按进程环境变量、`.env`、安全默认值加载配置。`.env.example` 当前已有 `LLM_PROVIDER=fake`、`LLM_MODEL=unset` 和空的 `LLM_API_KEY`；Fake 默认不要求密钥。
- T101 Parser Port 为 `job_agent.application.ports.JDParser`，唯一方法是同步 `parse(JDParseRequest) -> ParsedJD`。`JDParserError` 是解析执行阶段项目异常。
- 当前依赖中没有明确的 LLM Provider 或 HTTP 客户端约定；Streamlit 的传递依赖不能作为应用代码隐式依赖。
- `秋招投递智能体_AI开发文档包/06_Agent与Prompt规范.md` 要求结构化输出、hard/preferred 分离、缺失不猜测、Prompt 版本化及日志脱敏。该文档的一般 Agent 修复调用建议不覆盖本任务明确的有限重试策略。

## 4. Provider 与传输方案

采用唯一适配器 `OpenAICompatibleJDParser`，只对接 OpenAI-compatible Chat Completions 协议，不并行实现 OpenAI、Azure、Anthropic 或其他供应商专用适配器。

- Provider 标识：`openai_compatible`；适配器位于 infrastructure，application Port 不出现 Provider 名称、HTTP 类型、SDK 类型或供应商配置。
- `LLM_BASE_URL` 默认是 `None`/空值，没有任何真实服务默认地址。它表示调用方显式提供的兼容 API 根地址，不提供运行时自动探测或隐式本机地址，也不默认指向任何 OpenAI、DeepSeek、本地服务或其他 Provider。允许调用方明确填写公网 HTTPS 地址或本地 OpenAI-compatible HTTP 服务；适配器保留合法既有路径，规范化结尾斜线后只追加一次 `chat/completions`，配置值本身不得包含该资源路径。
- HTTP 客户端选择 `httpx` 同步客户端，而非供应商官方 SDK。理由：T101 Port 和工程调用栈同步；`httpx.MockTransport` 可完全离线验证 HTTP 行为；无需让领域、应用或 Port 绑定 SDK。生产请求需显式关闭客户端时通过上下文/生命周期接口关闭，不在模块导入时构造客户端。
- 新增直接运行依赖 `httpx>=0.27,<1.0`，不要依赖 Streamlit 的传递依赖。实施时先检查 Python 3.11 兼容性和依赖解析，再在 `pyproject.toml` 中声明。
- JSON Schema structured output 是唯一正常请求模式。若 Provider 不支持请求所需的 `response_format`，按 Provider/HTTP 错误失败；不得退化为自由文本、正则抢救或另一种隐式协议。

该方案不改变 `JDParser`：调用方仍只依赖 `JDParser` / `JDParserError`，装配层决定注入 Fake 或 `OpenAICompatibleJDParser`。应用 Port 不接收 URL、模型名、API Key、HTTP Client 或供应商异常。

## 8. 配置设计

扩展 `Settings` 和 `.env.example`，保持环境变量 > `.env` > 默认值。字段语义如下：

| 配置 | 语义 |
|---|---|
| `LLM_ENABLED` | 显式总开关，默认 `false`。真实适配器在 `false` 时必须于发送请求前以配置异常失败。不得因设置了 Key 就自动启用。 |
| `LLM_PROVIDER` | 只接受 `fake` 与 `openai_compatible`。默认 `fake`。其他值以不回显密钥的配置异常失败。 |
| `LLM_MODEL` | Provider 指定的模型标识；真实适配器要求非空且不能是默认占位值 `unset`。不得自动选择模型。 |
| `LLM_API_KEY` | OpenAI-compatible Bearer 凭据。真实适配器必需；Fake 不读取、不需要。只允许出现在 `Authorization: Bearer ...` Header。 |
| `LLM_BASE_URL` | 默认 `None`/空值，不设真实服务默认地址。Fake 和关闭状态可为空；启用 `openai_compatible` 时必须显式提供。只允许绝对 `http`/`https` URL、有 host、无 userinfo/query/fragment，且路径不含 `chat/completions`。测试通过注入 MockTransport，不访问该地址。 |

真实调用必须同时满足 `LLM_ENABLED=true`、`LLM_PROVIDER=openai_compatible`、显式有效 `LLM_MODEL`、`LLM_API_KEY` 和合法 Base URL。任何缺失/不支持配置都在网络请求前失败。`LLM_ENABLED` 不得改变 T101 Fake 的行为；应用启动及默认 `python -m job_agent` 不得为了校验配置而连接 Provider。

### 配置真值表

| `LLM_ENABLED` | `LLM_PROVIDER` | 构造与运行行为 |
|---|---|---|
| `false` | `fake` | 默认配置；完全离线。Fake 不读取、不要求 model、API Key 或 Base URL。Settings 可构造，Parser 装配选择 Fake。 |
| `false` | `openai_compatible` | 不允许真实 parse。为兼容 T001，Settings 仍先执行既有“非 Fake 必须有 Key”校验；Key 存在时，即使 model 为 `unset`/空值且 Base URL 为 `None`/空值，Settings 仍可加载。适配器 `parse()` 必须先检查 enabled，并以“未启用”配置错误零网络失败，不能让缺失 model/Base URL 覆盖该主要结果。 |
| `true` | `fake` | 仍使用 Fake、完全离线且不要求 API Key；开关仅授权已选择且配置完整的真实 Provider，不会把 Fake 自动换成真实实现。 |
| `true` | `openai_compatible` | 只有 model、Key、Base URL 均完整合法时允许装配真实适配器；构造阶段仍不请求网络，首次 `parse()` 才可发送请求。 |
| `true` | `openai_compatible`，model/Key/Base URL 任一缺失 | Settings 或装配阶段抛对应 `ConfigurationError`，请求计数为零；不得用默认模型、默认 Key 或自动发现地址补齐。 |
| 任意值 | 未知 Provider | 缺 Key 时为兼容 T001 先报 `LLM_API_KEY` 缺失；Key 存在时明确报不支持 Provider。不得猜测别名或自动路由。 |

默认 `.env.example` 必须是 `LLM_ENABLED=false`、`LLM_PROVIDER=fake`，因此完全离线。环境或 `.env` 中偶然存在 `LLM_API_KEY` 绝不能改变 enabled/provider，也不能自动创建真实适配器或触发网络。

兼容现有 T001 设置测试：配置校验顺序固定为先解析 enabled/provider，再对所有非 `fake` Provider 执行现有缺 Key 校验，然后校验 Provider 白名单；**只有** `enabled=true` 且 Provider 为 `openai_compatible` 时才校验 model 和 Base URL 的完整性与合法性。这样：

- `LLM_PROVIDER=openai` 且缺 Key 时仍产生提及 `LLM_API_KEY` 的 `ConfigurationError`；若 Key 齐全，则 `openai` 作为未知值被拒绝，不是 `openai_compatible` 的别名；
- `enabled=false + openai_compatible + Key 存在` 时不要求 model/Base URL 完整，Settings 可加载；适配器 `parse()` 先报告未启用且请求计数为零；
- `enabled=true + openai_compatible` 时 Key、有效 model、合法且显式的 Base URL 缺一不可，任一缺失均在请求前失败。

### API Key 类型与泄漏边界

`Settings.llm_api_key` 保持当前公共类型 `str | None`，不在 T102 擅自改为 Pydantic `SecretStr`，避免破坏 T001 调用方和测试。用 `dataclasses.field(default=None, repr=False)` 或兼容的自定义安全 `__repr__` 隐藏该字段；不得改变正常属性读取语义。

API Key 只允许在适配器构造请求时进入 `Authorization: Bearer <key>` Header。不得进入请求 JSON、Prompt、trace_id、URL/query、异常、日志、指标或对象 repr。测试必须使用明显哨兵值（例如 `T102_FAKE_KEY_MUST_NOT_LEAK`），同时捕获 repr、异常和运行日志确认不泄漏。仓库、`.env.example`、Fixture、文档和测试输出禁止出现真实 Key。

### Base URL 规范化与校验

- `Settings.llm_base_url` 使用 `str | None` 或等价可空类型，环境变量缺失或 `LLM_BASE_URL=` 统一归一化为 `None`。不得在字段默认值、`from_env()`、适配器或 bootstrap 中填入任何真实服务地址。
- 仅接受绝对 `http` 或 `https` URL，必须有 host；拒绝相对地址、其他 scheme、userinfo、query 和 fragment。
- 配置值表示 API 根路径，可以是无路径根地址，也可以包含 `/v1`、`/api/openai/v1` 等既有代理路径；现有路径必须保留。
- 去掉路径结尾的一个或多个 `/` 后追加且只追加一次 `/chat/completions`。例如 `https://llm.example.test/v1/` 得到 `https://llm.example.test/v1/chat/completions`。
- 拒绝路径内部双斜线，避免歧义；scheme 后的 `://` 不计入。拒绝已经以 `/chat/completions` 结尾或在路径中包含该资源段的误填完整 endpoint，不进行重复追加或静默修正。
- 测试覆盖无/有尾部斜线、多个尾部斜线、内部双斜线、合法既有路径、误填完整 endpoint、userinfo/query/fragment 和本地显式 HTTP 地址。
- 配置错误使用固定安全 message，只指出字段/错误类别，不回显原始 URL；尤其不得回显 userinfo 或 query 中可能携带的认证信息。
- 不读取 OpenAI/DeepSeek/其他 SDK 的默认地址，不扫描 localhost 端口，不根据 Provider 名猜测 endpoint。只有用户显式配置的地址才可在满足全部开关后被 `parse()` 使用。

不得把配置值、Key、认证 Header 或完整 Base URL 写入错误文本、日志、测试断言输出或文档。Settings 的 repr/安全展示不得打印 API Key；如现有配置对象 repr 会显示 Key，应在 T102 最小修正并测试。

## 9. 信任边界

可信输入仅来自调用方已校验的 `JDParseRequest`：`raw_jd`、`source_url`、`source_name`、`external_job_id`、`trace_id`。其中只将解析必需的 `raw_jd` 发给模型。来源字段由适配器从原请求重新注入结果；`trace_id` 仅用于本地日志关联，不进入 HTTP body 或 `ParsedJD`。

不可信输入包括模型返回的每个字段、Provider 错误文本和 raw JD 中可能出现的 Prompt Injection。JD 原文是待分析数据，不是系统指令。Provider 输出不能决定或覆盖 `raw_jd`、来源元数据、`trace_id`、ID、fingerprint、discovered_at、数据库状态或任何候选人事实。

原始 JD 可能带有个人或认证信息；本任务按“必要字段最小化”只发送原始 JD，不附带 Profile、Evidence、简历、Application、数据库内容、API Key 或本机路径。不得向模型发送 `trace_id` 或认证信息。

## 10. 模型输出契约

在 `infrastructure/llm/schemas.py` 定义严格 `JDParserModelOutput`（名称可微调），字段只包含既有 `ParsedJD` 的语义部分：

- `title`、`company`、`location`、`job_type`；
- `responsibilities`、`hard_requirements`、`preferred_qualifications`、`skills`；
- `education_requirement`、`experience_requirement`、`graduation_requirement`、`languages`；
- `deadline`、`deadline_text`、`ambiguous_items`。

输出 Schema 必须 `extra="forbid"`。为适配严格 JSON Schema 模式，响应对象中的每个语义 key 均要求出现；允许缺失事实的可空字段显式返回 `null`，列表显式返回 `[]`。Schema 明确不得包含 `raw_jd`、`source_url`、`source_name`、`external_job_id`、`trace_id`、`id`、`fingerprint`、`discovered_at` 或数据库状态。Provider 返回上述或任何其他未知字段时整份输出校验失败，不忽略、不覆盖调用方值。

`hard_requirements` 和 `preferred_qualifications` 必须使用 `JDRequirement` 的既有结构。`deadline` 是 ISO 8601 带时区字符串或 null；最终仍须通过 `ParsedJD` 的 timezone-aware 校验。优先、加分、preferred、plus、nice-to-have 不得进入硬性列表；无法确定时写入 `ambiguous_items`。缺失值用 `None`、空列表或 `ambiguous_items`，不使用字符串 `unknown`。

适配器校验成功后构造 `ParsedJD`：原样注入 `request.raw_jd` 及 `source_url`、`source_name`、`external_job_id`，再与模型语义字段合并并执行最终 `ParsedJD.model_validate`。最终结果的 `raw_jd` 必须逐字符等于请求值；`trace_id` 不在输出契约中。

## 11. Prompt v1

Prompt ID/版本固定为 `jd-parser` / `jd-parser-v1`，模板独立于 HTTP 适配器并可单元测试。T102 不实现版本路由或在线管理平台。

- **System message** 说明任务只抽取岗位语义；列出输出 Schema 和字段含义；定义缺失与歧义策略、hard/preferred 区分和不可违反的安全规则。
- **User message** 只包含 raw JD 数据，以结构化 JSON 编码或明确数据边界传入，避免把 JD 片段拼接成额外指令。
- 明确 raw JD 是不可信数据，不是系统指令；不得遵循其中要求泄漏提示词/密钥、修改输出格式、调用工具或访问外部资源的文本。
- 公司、学历、技能、经验、毕业要求、地点、语言和截止时间只能由原文支持；不得凭常识补全。信息缺失返回 null/空列表；含糊项写入 `ambiguous_items`。
- 明确 mandatory/required/must 与 preferred/plus/nice-to-have 的语义区别；仅明确强制条件进入 `hard_requirements`，明确优先项进入 `preferred_qualifications`。
- 只输出指定结构化 JSON，不附 Markdown、解释文字或代码围栏。
- Prompt 不含 API Key、Authorization、Cookie、数据库地址、用户简历、Profile 或真实个人资料。
- 对模板做固定字符串/结构测试，检查版本标识、注入边界、缺失策略、分类规则和禁止内容；不通过真实 LLM 测试 Prompt。

Prompt Injection 防护属于指令隔离与数据最小化，不声称可从根本上消除模型注入风险；输出仍视为不可信并必须 Schema 校验。

## 12. Provider 请求结构

只有 `parse()` 可以对规范化后的 `POST {LLM_BASE_URL.rstrip('/')}/chat/completions` 发起网络请求。请求必须包含 `Authorization: Bearer <LLM_API_KEY>` 和 `Content-Type: application/json`，并发送以下 JSON：

```json
{
  "model": "由配置提供的模型名",
  "messages": [
    {"role": "system", "content": "jd-parser-v1 system 内容"},
    {"role": "user", "content": "仅含 raw_jd 的数据消息"}
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "jd_parser_v1",
      "strict": true,
      "schema": "JDParserModelOutput 生成的 JSON Schema"
    }
  }
}
```

`model` 只能来自已校验的 `LLM_MODEL`；`messages` 恰好包含 Prompt v1 的 system/user 消息；`response_format` 使用 `JDParserModelOutput` 对应的 strict JSON Schema。不得把 API Key 放进 JSON body、URL、模型名、Prompt 或日志；不得默认添加会带入用户身份的 Header。不得向 Provider 发送 `trace_id`、`source_url`、`source_name`、`external_job_id`、Profile、Evidence 或其他解析不需要的元数据。

必须显式配置有限超时。推荐 connect 5 秒、read 20 秒、write 5 秒、pool 5 秒；这些是单次请求限制，不得设置无限超时。HTTP Client、Transport 和 sleeper 通过构造参数注入，便于使用 `httpx.MockTransport`；生产默认客户端不得在 import 时创建。

### HTTP Client 所有权与生命周期

适配器必须支持并测试两种互斥所有权：

- **外部注入 Client**：构造器接收现成 `httpx.Client` 时，所有权属于调用方。Parser 的 `close()` 或退出上下文不得关闭该 Client；调用方负责最终关闭。Parser 可以在自身关闭后拒绝继续使用该 Client。
- **内部 Client**：未注入 Client 时，Parser 只在首次需要真实 `parse()` 时惰性创建 Client，并拥有它。Parser 提供幂等 `close()` 及同步 context manager（`__enter__`/`__exit__`），关闭时释放内部 Client。不得依赖垃圾回收作为正常关闭路径。

模块 import、Settings 构造、Parser 构造及进入 context manager 都不得发起请求；只有合法且启用状态下的 `parse()` 才能联网。Parser 一旦 `close()`，无论 Client 所有权为何，后续 `parse()` 均在零网络调用前抛稳定 `JDParserClosedError`（或同等 `JDParserError` 子类），不得偷偷重建 Client。重复 `close()` 不报错。

不得在全局模块变量、单例或 import-time cache 中创建/缓存 Client。测试使用带关闭状态的 injected Client/Transport，分别断言外部 Client 未被 Parser 关闭、内部 Client 被正确关闭、context manager 释放资源、重复关闭安全以及 close 后 parse 不请求网络。

## 13. 响应解析与 Pydantic 校验

按固定边界处理，不做内容猜测：

1. 以受限流式读取或等价有界读取累计解压后的响应字节；超出第 14 节限制立即停止读取，并在 JSON 解析前失败。
2. 检查 HTTP 状态；HTTP 2xx 只代表传输成功，不代表解析成功。错误响应不得进入业务 JSON 解析，也不得把 Provider body 放入异常。
3. 将受限响应 envelope 解析为 JSON 对象；响应本身不是 JSON、顶层不是对象均失败。
4. `choices` 必须存在、是列表且长度**恰好为 1**。缺失、空列表或多个 choice 均拒绝；不得静默选择第一条。唯一 choice 的 `message` 必须是对象。
5. `finish_reason` 必须严格为 `"stop"`；`null`、`length`、`content_filter`、`tool_calls` 或其他值均失败。若 `message.refusal` 为任何非 null/非空值，立即以安全 Provider 拒绝异常失败，即使同时存在 content。
6. `message.content` 必须是非空、非纯空白字符串；null、数组、多模态块、对象或其他类型均拒绝。存在 tool call 或缺失 message/content 时失败。
7. 对 content 直接执行一次 JSON parse；拒绝 Markdown 代码围栏、前后解释文本、截断内容和非 JSON。不得用正则或子串截取从自然语言中抢救 JSON。
8. 将 JSON 直接通过严格 `JDParserModelOutput.model_validate_json()` / `model_validate()`。未知字段、缺字段、字段类型错误、非法枚举/列表元素、naive deadline 均失败；不静默丢弃、不自动修复、不将失败伪装成空结果。
9. 用已验证的语义数据与调用方可信字段构造 `ParsedJD` 并再做完整 Pydantic 校验。
10. 成功才返回 `ParsedJD`。失败返回项目级 `JDParserError` 子类并保留安全异常链；外部可见异常文本只含稳定错误 code/类别，不含原始内容、Provider body、认证信息或底层 URL。

模型试图返回 `raw_jd` 或来源元数据时，由 `extra="forbid"` 明确拒绝。所有模型语义字段均不因“格式看似可用”而跳过 Pydantic 校验。

## 14. 输入长度和成本边界

- 最大 `raw_jd` 长度固定为 **30,000 个 Python Unicode 字符**（`len(raw_jd)`），在任何 HTTP 请求之前检查；计数包含空白和换行，不先 trim 或规范化。
- 超限抛 `JDParserInputTooLongError`（或同等稳定项目异常），不发送请求、不记录原文。
- 不自动截断、摘要或拆分 JD 后继续解析；调用方必须明确缩短输入并重新提交。
- 不引入 Tokenizer/token 估算器依赖，不引入成本管理平台或计费数据库。
- Provider **解压后的响应体上限固定为 1,048,576 bytes（1 MiB）**，足以容纳本任务的 ParsedJD JSON。实现必须在累积读取时计数，并在 JSON/Pydantic 解析前拒绝第 1,048,577 个字节；不得先无界加载完整响应再检查。
- 响应超限抛固定的 Provider 响应过大异常，不保存部分/完整响应，不自动重试。测试精确覆盖等于上限与超一字节，并断言超限路径未调用 JSON/Pydantic 解析器。
- 日志不记录完整 raw JD、完整 Prompt 或完整响应；不得为调试默认保存这些内容。

## 15. 错误层次

新增异常均继承 T101 的 `JDParserError`，并使用稳定、可测试的错误类别/code。异常 message 不包含敏感值；异常 chaining 可供受控调试保留，但 UI/日志边界不得直接打印原始 cause/traceback。

至少定义或明确映射以下类别：

| 类别 | 典型触发 | 重试 |
|---|---|---|
| 配置缺失/Provider 不支持/未显式启用 | Provider、模型、Key、Base URL 或开关无效 | 否 |
| 输入超长 | `raw_jd` 超 30,000 字符 | 否 |
| 请求超时 | HTTPX connect/read/write/pool timeout | 有限重试 |
| 网络不可用 | ConnectError、NetworkError 等连接失败 | 有限重试 |
| 认证/授权失败 | HTTP 401/403 | 否 |
| 限流 | HTTP 429 | 有限重试 |
| Provider 其他 4xx | 400/404/422 等非限流客户端错误 | 否 |
| Provider 暂时性服务失败 | HTTP 500、502、503、504 | 有限重试 |
| Provider 其他 5xx | 未列入暂时性白名单的 5xx | 否，除非实现有明确协议证据并测试 |
| Provider 响应为空/拒绝/结构错误 | 缺 envelope/content 或拒绝内容 | 否 |
| 非法 JSON/围栏/多余文字 | 内容无法直接作为 JSON 解析 | 否 |
| 输出 Schema 错误 | 缺字段、额外字段、类型错误、naive deadline | 否 |
| 重试耗尽 | 可重试错误达到最大次数 | 已终止；保留安全的最后错误类别 |

`JDParserError` 是上层调用唯一需要捕获的基类。不得将 `httpx`、Pydantic 以外部原始异常直接泄漏成 Port 行为；Pydantic `ValidationError` 只用于 caller 构造输入请求，适配器处理模型输出时应转换成项目级解析错误。

## 16. 超时与重试矩阵

单次 `parse()` 的**最大 HTTP 总尝试次数为 3 次，包含首次请求**。0.5 秒在第 2 次尝试前执行，1.0 秒在第 3 次尝试前执行；若第 1/2 次错误不可重试，则不 sleep、不再请求。最大本地退避总时长为 1.5 秒，不加 jitter。

| 错误/状态 | 是否重试 | 最大 HTTP 尝试 | 规则 |
|---|---:|---:|---|
| 配置错误、未启用、Client 已关闭 | 否 | 0 | 在请求前失败。 |
| 输入超长 | 否 | 0 | 在请求前失败，不截断。 |
| HTTP 400/404/422 | 否 | 1 | 永久客户端/协议错误。 |
| HTTP 401/403 | 否 | 1 | 认证/授权错误，不盲目重试。 |
| HTTP 408 | 是 | 3 | 视为暂时请求超时，按 0.5/1.0 秒退避。 |
| HTTP 409 | 否 | 1 | 不推断冲突可恢复。 |
| HTTP 429 | 是 | 3 | 按本地固定退避；T102 **不采用 `Retry-After`**，避免不可信/超长等待，单次等待上限因此为 1.0 秒。 |
| HTTP 500/502/503/504 | 是 | 3 | 暂时性服务错误，按固定退避。 |
| 其他 5xx | 否 | 1 | 未进入白名单，不自动重试。 |
| HTTPX 连接失败/网络不可用 | 是 | 3 | 使用同一请求，按固定退避。 |
| HTTPX connect/read/write/pool timeout | 是 | 3 | 使用同一请求，按固定退避。 |
| 空响应、拒绝、envelope/choice/content/finish_reason 错误 | 否 | 1 | 已产生一次可能计费的成功响应，不自动再次调用。 |
| 响应体超过 1 MiB | 否 | 1 | 解析前失败，不再次计费。 |
| 非 JSON、Markdown 围栏、前后解释文本 | 否 | 1 | 不做修复调用或内容抢救。 |
| Pydantic 校验失败，包括未知字段、类型错误、naive deadline | 否 | 1 | 视为永久输出错误，不做修复调用。 |

本任务不实现设计文档中的二次“修复调用”：任何已收到 HTTP 成功响应但内容无效的场景都不自动再次计费。若未来需要修复策略，必须另行定义独立预算、Prompt、可观测性和用户授权，不能在 T102 隐式加入。

每次重试使用相同请求，不修改 raw JD、不添加修复指令、不更换模型。`sleep(seconds)` 从构造器注入；单元测试使用记录参数的 fake sleeper，严禁真实等待，并断言只有将要执行下一次 HTTP 请求时才 sleep。

重试耗尽抛稳定 `JDParserRetriesExhaustedError`（或同等异常）。最终异常以一个已经脱敏的项目级传输/状态异常作为 `__cause__`，保留最后错误类别和异常链；不得直接链接或展示含 Provider body、完整 URL、Header、Key 或 JD 的原始 Response/异常文本，也不得吞掉错误或返回空 `ParsedJD`。

## 17. 脱敏与可观测性

使用标准库 `logging`，可由构造器注入 logger；不引入大型可观测平台、全局 logging 初始化或 import-time handler。日志以事件/额外字段形式记录，不拼接任意 Provider 文本。

允许记录：`trace_id`（如提供）、Prompt ID/version、Provider 标识、模型标识、尝试次数、HTTP 状态分类、延迟毫秒、成功/失败类别。模型名和 trace_id 不得包含未经长度限制的输入文本；必要时做长度/字符限制。

绝不记录：API Key、Authorization、Cookie、raw JD 全文、完整 Prompt、完整响应、Provider 错误 body、数据库 URL、完整本机路径。默认也不记录请求/响应摘要，除非摘要仅是不可逆哈希且确有调试需要；本任务不要求哈希日志。

对外项目异常只使用错误 code 和不含敏感值的固定安全 message。日志参数不得含 HTTP Request/Response 对象、Header 映射、Prompt 字符串或完整异常 repr。测试使用显眼假 Key、假 Cookie、假敏感 JD，并检查 caplog、异常文本和请求 body，断言所有禁止值均不出现。

## 18. 依赖方向

- `application.ports.JDParser`、T101 contracts、`domain` 不导入 `httpx`、SDK、`infrastructure`、Prompt 或配置模块。
- `infrastructure.llm` 可以依赖既有 Port、contracts、domain 校验、`Settings`、httpx 和标准库；不得让 application/domain 依赖它。
- Adapter 的返回只能是 `ParsedJD`，错误只经 `JDParserError` 子类；不返回 HTTP Response、dict envelope 或 ORM。
- T101 Fake 和其 Fixture 加载方式保持原样及向后兼容；T102 不要求 Fake 读取 Settings 或 API Key。
- 配置对象由 composition/bootstrap 层读取并注入 Adapter；模块 import 不读取 `.env`、创建 Client、连网或建立数据库连接。
- HTTP Client/Transport/sleeper/logger 显式注入；资源关闭责任要有确定的上下文/close 约定，不能留下隐式未关闭 Client。

## 19. 测试规划

默认所有自动化测试严格离线，使用 `httpx.MockTransport`、stub client 或等价依赖注入，不 monkeypatch 真实公网 DNS，不依赖真实 Provider 可用性，不读真实 `.env`。测试不使用真实 Key，只用哨兵值。

至少覆盖：

- 成功响应转 `ParsedJD`；hard/preferred 正确分离；缺失字段保留 None/空列表/ambiguous；

- 成功/异常后均不记录假 Key、Cookie、认证 Header、敏感 JD、完整 Prompt、response body 或数据库 URL；
- 超时、连接失败、401/403、不重试 4xx、429、可重试 5xx、非重试 5xx、退避次数、重试耗尽及注入 sleeper；

- `isinstance(adapter, JDParser)` 成立，Port 仍只有同步 `parse`；application/contracts、ports/domain 无新增禁用依赖；

- 原有 T101 契约/Fake 专项及完整 172 项基线回归继续通过；如新增测试改变总数，交付文档以真实测试结果为准。
