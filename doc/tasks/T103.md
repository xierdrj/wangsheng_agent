# T103：Search Plan 与 Greenhouse 岗位源接口

## 1. 任务目标

T103 为 V0.2 岗位发现链路定义一个可验证、可替换、默认离线的搜索边界。本任务只交付后续实现可以直接遵循的规格，不实现生产代码、网络调用、数据库写入或 UI。

本任务的唯一正式岗位源为 Greenhouse Job Board API。T103 的交付目标是：

- 在 application 层定义确定性、可验证的 `SearchPlan` 输入契约；
- 在 `job_agent.application.ports` 定义唯一的 `JobSource` 查询 Port；
- 定义 Greenhouse 原始岗位的脱供应商耦合契约和适配器行为；
- 明确 board allowlist、默认离线、网络触发和授权边界；
- 规定整体获取、确定性本地筛选、稳定排序和内分页；
- 固定有限重试、错误分类、响应大小限制、资源生命周期和可观察性；
- 为 Fake、脱敏 Fixture、`httpx.MockTransport` 离线测试和后续实现提供验收标准；
- 保证来源层结果不会冒充最终 `JobPosting`，也不会调用 T102 Parser、`JobService` 或 Repository。

T103 不新增或修改生产代码。本文件是 T103 的唯一交付文件。

## 3. 术语定义

- **SearchPlan**：application 层的、确定性且可验证的查询计划。它表达要访问哪些已授权 board 以及如何在本地筛选、排序和分页，不是 LLM Prompt，也不是 HTTP 请求对象。
- **board token**：Greenhouse Job Board API URL 中的组织招聘板标识。它是显式配置的目标标识，不等同于 API Key、密码或认证凭据。
- **board allowlist**：部署者明确允许访问的 board token 集合。未在集合内的 token 即使格式正确也拒绝。
- **JobSource Port**：application 层唯一的岗位源查询抽象，向上层返回来源层契约，不暴露 HTTP 或供应商 SDK 类型。
- **GreenhouseRawJob**：Greenhouse 响应经 Schema 校验后的原始岗位记录，保留来源字段和原始内容，不是 `JobPosting`。
- **来源层结果**：`JobSourceResult` 及其 `GreenhouseRawJob` 项目；它不包含数据库 ID、fingerprint、`discovered_at` 或匹配结论。
- **本地筛选**：适配器在已获取的官方列表上按 `SearchPlan` 规则执行的确定性筛选，不使用 LLM，不调用 Parser。
- **内部分页**：本地筛选和排序完成后，对完整结果集合应用 `offset`/`limit`；不表示远端请求使用了分页参数。
- **整体失败**：单个 board 请求经过规定重试仍失败时，本次多 board 查询抛出错误，不返回其他 board 的不完整结果。
- **空结果**：请求成功、响应和所有记录通过校验，但筛选后没有岗位；这是成功结果，不是错误。

## 7. SearchPlan 输入契约

正式契约建议定义为 Pydantic 模型，默认 `extra="forbid"`。字段语义如下：

```python
class SearchPlan(BaseModel):
    boards: tuple[str, ...]
    keywords: tuple[str, ...] = ()
    locations: tuple[str, ...] = ()
    departments: tuple[str, ...] = ()
    offices: tuple[str, ...] = ()
    sort_by: Literal["updated_at", "title", "location", "external_job_id"] = "updated_at"
    sort_order: Literal["asc", "desc"] = "desc"
    offset: int = 0
    limit: int = 50
    trace_id: str | None = None
```

实现可把字段拆成值对象，但必须保持以下语义：

- `boards` 非空；每个 token 去除首尾空白、只允许 ASCII 字母、数字、短横线和下划线，长度有明确上限；规范化后不得重复；
- `keywords`、`locations`、`departments`、`offices` 的元素去除首尾空白，空字符串拒绝，规范化后去重；不把这些值当作 SQL、正则或 URL 片段执行；
- 关键词和筛选文本只作为本地字符串匹配输入，不能包含未经定义的通配符语义；
- `offset >= 0`，`1 <= limit <= 100`；超界或类型错误在构造计划时失败；
- `sort_by` 和 `sort_order` 只接受列出的枚举值；不接受任意字段名或客户端传入表达式；
- `trace_id` 仅用于日志关联，禁止承载 API Key、Cookie、密码或完整岗位文本；
- 计划构造不得读取网络、环境中的秘密、数据库或 Fixture；
- 计划必须可序列化为稳定 JSON 以便审计，序列化顺序和规范化规则固定；
- 计划不是远端 Greenhouse 请求参数。第一版不把 `keywords`、地点或排序字段映射成未获官方证据支持的远端 query 参数。

`SearchPlan` 的验证错误必须指出字段和错误代码，不回显完整输入文本、密钥、绝对路径或 HTTP 响应内容。allowlist 校验可以在适配器构造或 `search()` 开始时执行，但必须早于任何 Client 请求。

## 8. SearchPlan 输出契约

正式 Port 返回来源层结果，建议契约为：

```python
class JobSourceResult(BaseModel):
    source: Literal["greenhouse_job_board"]
    items: tuple[GreenhouseRawJob, ...]
    total: int
    offset: int
    limit: int
    has_more: bool
    boards: tuple[str, ...]
    fetched_count: int
    filtered_count: int
```

约束：

- `items` 是当前 `SearchPlan` 在本地筛选、稳定排序后切片的结果；
- `total` 等于所有允许 board 聚合、去重、筛选和排序后的结果数，发生本地分页前计算；空结果时为 0；
- `filtered_count` 与 `total` 的含义必须固定，建议二者相等；如实现保留原始未分页计数，必须另起明确字段，不能复用 `total`；
- `fetched_count` 是通过官方列表成功校验的原始岗位记录数，不能把失败 board 的未知数量当作 0；
- `has_more = offset + len(items) < total`；
- `items` 不含 `JobPosting`、ORM、Response、Client 或 Session；
- `source` 是稳定来源标识，不是 URL，也不携带秘密；
- 不对结果自动持久化、不生成 fingerprint、不生成数据库 `id` 或 `discovered_at`。

## 9. JobSource Port

在 `job_agent.application.ports.job_source` 定义唯一正式查询接口：

```python
class JobSource(Protocol):
    def search(self, plan: SearchPlan) -> JobSourceResult: ...
```

Port 要求：

- 只定义这一套正式岗位查询方法；不得同时暴露 `search_jobs()`、`list_jobs()`、`fetch()` 等重叠公共入口；
- 参数和返回值只能是标准库类型、Pydantic 契约或领域值对象；
- 不出现 `httpx`、`httpx.Response`、SQLAlchemy、ORM、Session、Streamlit、LangGraph、Playwright、供应商 SDK 或配置实现类型；
- Port 不负责 HTTP Client 生命周期、认证头、重试、数据库事务、fingerprint、JobService 或 Parser；
- 方法同步，和当前 Service、Repository、T101/T102 Port 保持一致；
- 非法计划、allowlist 拒绝在请求前失败；外部失败通过项目级异常可见；
- 空结果是正常的 `JobSourceResult`，不能用 `None`、旧缓存或虚构岗位代替；
- Port 的实现必须可以由 Fake 完整替换，以便普通 pytest 完全离线。

建议错误根类 `JobSourceError`，下列子类只表达稳定业务分类，不泄漏底层异常全文：

```text
SearchPlanValidationError
BoardNotAllowedError
JobSourceConfigurationError
GreenhouseHTTPError
GreenhouseAuthenticationError       # 401/403
GreenhouseBoardNotFoundError        # 404
GreenhouseTimeoutError
GreenhouseConnectionError
GreenhouseRateLimitedError          # 429，重试耗尽后
GreenhouseServerError               # 5xx，重试耗尽后
GreenhouseInvalidJSONError
GreenhouseResponseTooLargeError
GreenhouseSchemaValidationError
GreenhouseRetriesExhaustedError
```

## 10. Greenhouse Job Board API 适配器

适配器位于 infrastructure，例如 `job_agent.infrastructure.job_sources.greenhouse`。它实现 `JobSource`，但不改变 Port 的签名。

官方能力和本任务使用方式：

- Greenhouse 官方 Job Board API 提供公开 GET 的 board jobs 列表能力；官方文档示例路径为 `https://boards-api.greenhouse.io/v1/boards/{board_token}/jobs`；
- 官方文档还描述了按岗位 ID 获取单个岗位的 GET 能力，但 T103 第一版只把列表 GET 作为 `search()` 的内部来源；单岗位获取需后续独立任务提供独立理由和测试；
- `content=true` 是官方列表接口文档中用于请求岗位内容的显式参数，适配器可固定发送该参数，以便来源层保留正文；
- T103 不把岗位关键词、地点、部门、办公室、排序、`page`、`cursor` 或 `page_size` 发送为自定义远端参数，除非后续任务以新的官方证据和验收标准扩展；
- 不把 API Key 虚构为公开 Job Board GET 的必要条件，不默认发送 `Authorization`；若未来组织配置要求额外认证，必须作为独立任务审查，不能偷偷加入；
- 适配器只访问 `boards-api.greenhouse.io` 的 API URL，不访问 `boards.greenhouse.io` 招聘网页 HTML。

适配器构造时只保存已校验配置和依赖，不创建网络请求。首次 `search()` 前必须完成计划和 allowlist 校验。每次 `search()` 对计划列出的每个 board 发出一次整体列表 GET；多 board 按计划顺序访问，结果随后按统一稳定键合并。

## 11. board allowlist 和配置规则

配置至少需要以下语义（具体环境变量名称可由实现任务确定，但不得改变默认值和安全含义）：

```text
JOB_SOURCE_NETWORK_ENABLED=false
GREENHOUSE_ALLOWED_BOARDS=       # 默认空集合
GREENHOUSE_REQUEST_TIMEOUT_SECONDS=10
GREENHOUSE_MAX_RESPONSE_BYTES=1048576
GREENHOUSE_MAX_ATTEMPTS=3
GREENHOUSE_BACKOFF_SECONDS=0.5,1.0
```

规则：

1. `JOB_SOURCE_NETWORK_ENABLED` 默认 `false`。未显式设置为真时，调用直接抛配置错误，不创建请求，也不建立到 API 的连接。
2. allowlist 默认空。没有默认 board token、默认组织、环境变量猜测值或代码常量回退。
3. allowlist 中的 token 必须逐项规范化、校验格式、去重；空白 token、通配符、URL、路径、查询串和控制字符拒绝。
4. `SearchPlan.boards` 必须是 allowlist 的子集；任一 board 不在 allowlist 时，在任何网络请求前抛 `BoardNotAllowedError`。不得只过滤掉非法 board 后继续访问合法 board。
5. 不自动发现、枚举、试探或从组织名称推导 board token；不从 Greenhouse 网页、搜索引擎或响应中的其他字段扩展 allowlist。
6. 网络开关为真、配置合法且全部 board 通过 allowlist 后，才允许创建/使用 HTTP Client。
7. 配置错误不得回显 API Key、Cookie、Authorization、完整 URL 中的敏感部分或 `.env` 内容；配置对象的 `repr` 必须脱敏。
8. live smoke 只能显式 opt-in，并且使用获得目标组织授权的 board；普通 pytest 不读取真实环境的 board 配置。

## 12. endpoint、请求参数与响应规则

第一版固定请求：

```text
GET https://boards-api.greenhouse.io/v1/boards/{board_token}/jobs?content=true
Accept: application/json
```

请求规则：

- `{board_token}` 只能来自已校验的 allowlist 计划，必须使用 URL path 参数编码器，不进行字符串拼接注入；
- 不发送 `Authorization`、API Key、Cookie、候选人资料、Profile、trace_id 或 LLM Prompt；
- 可发送固定、非敏感的 `User-Agent`，不包含个人信息和密钥；
- 第一版不得增加未被官方文档确认的分页或过滤 query 参数；
- 查询超时、响应大小上限、最大尝试次数和退避由配置注入并有安全上限；
- 只接受成功的 JSON 响应；状态码与 JSON 解析/Schema 失败分别分类。

响应规则：

- 列表 envelope 必须是 JSON object，`jobs` 必须是 array；每个元素必须通过 `GreenhouseRawJob` Schema；
- 若官方响应提供 `meta.total`，可保存为非业务观测字段 `remote_total`，但不得把它当作本地筛选后的 `total`，也不得据此假设有分页；
- `jobs` 缺失、非数组、元素不是 object、字段类型不符或 JSON 非法，整次请求失败；不得跳过坏记录后返回不完整结果；
- 缺失的可选字段保持 `None` 或空列表；禁止以“未知”、空字符串或猜测值填充事实字段；
- 原始 `content` 为空时保留 `None`/空值，由后续 Parser 决定如何处理；不能从 HTML 网页补齐；
- 响应主体在解压后超过上限时失败，不把截断 JSON 当作有效结果；
- 未知 JSON 字段可按适配器策略保留在受控 `metadata`，但不得让未知字段绕过核心 Schema；更保守的第一版可拒绝未知核心字段并忽略非核心扩展字段，必须由测试固定。

## 13. Greenhouse 原始岗位契约

`GreenhouseRawJob` 是 application 可消费的来源层 Pydantic 契约。字段以官方 Job Board API 文档的公开 JSON 为事实来源，建议至少覆盖：

```python
class GreenhouseRawJob(BaseModel):
    board_token: str
    id: int
    internal_job_id: int | None = None
    requisition_id: str | None = None
    title: str
    updated_at: datetime | None = None
    location: GreenhouseLocation | None = None
    absolute_url: HttpUrl
    content: str | None = None
    departments: tuple[GreenhouseDepartment, ...] = ()
    offices: tuple[GreenhouseOffice, ...] = ()
    metadata: tuple[GreenhouseMetadataItem, ...] = ()
```

实现时必须以官方文档和脱敏响应确认具体字段类型；以上不是允许虚构字段的理由。契约要求：

- `id` 与 `board_token` 联合作为来源层稳定主键；不要把裸 `id` 当作跨组织全局 ID；
- `absolute_url` 只接受合法 HTTP(S) URL；不访问该 URL，也不以 HTML 内容替代 API `content`；
- `updated_at` 若带时区则保留 aware datetime；缺少或无法解析时为 `None` 并记录 Schema/数据质量事件，不能使用本机时间猜测；
- location、department、office 的名称缺失时保持空值/空列表；不从标题或正文推断地点；
- `content` 是供应商原始岗位内容，必须按响应原文保存于本次运行内存结果；不得在错误消息和日志中回显全文；
- metadata 仅作为受控、可脱敏的供应商附加字段，不得被当作候选人事实；
- 原始契约默认 `extra="forbid"` 或采用明确的扩展字段白名单；Schema 变更需要新的测试和文档版本；
- 契约不包含 `company`、`fingerprint`、数据库 `id`、`discovered_at`、match 分数或 `ParsedJD` 专属结论，除非官方响应确实提供并在新任务中明确定义。

## 14. 原始岗位、ParsedJD 与 JobPosting 的边界

三者关系固定如下：

| 层次 | 责任 | 允许缺失 | 禁止行为 |
| --- | --- | --- | --- |
| `GreenhouseRawJob` | 保留官方 API 原始字段、board 和岗位 ID | 可选 API 字段为 `None`/空列表 | 不解析事实、不算 fingerprint、不写库 |
| `ParsedJD` | T101/T102 对原始 JD 文本的结构化中间结果 | 标题、公司、要求、截止日期可缺失并保留歧义 | 不调用搜索、不补事实、不创建 Job |
| `JobPosting` | T002/T006 的持久化岗位领域对象 | 持久化所需字段应完整 | 不由 T103 直接构造或保存 |

T103 只返回来源层 `JobSourceResult`。适配器不得：

- 调用 T102 `JDParser.parse()`；
- 把 GreenhouseRawJob 转成 `ParsedJD`；
- 填充虚构的 company/title/location/deadline；
- 生成 `JobPosting.id`、`fingerprint` 或 `discovered_at`；
- 调用 `JobService.save_manual_job()`、Repository、Unit of Work 或数据库；
- 将 API `id` 误用为领域 `JobPosting.id`。

后续 T104 或独立任务才可以规定 RawJob → NormalizedJob/ParsedJD → `JobPosting` 的转换和持久化边界。

## 15. 确定性本地筛选

第一版获取每个允许 board 的官方完整列表后，在内存中按 `SearchPlan` 进行确定性筛选：

1. 对用于匹配的文本执行 Unicode NFC、首尾空白去除、连续空白折叠和 `casefold()`；保留原始字段，不覆盖来源文本。
2. `keywords`：每个关键词必须在标题、content、location 名称、department 名称、office 名称和 requisition/title 等已明确字段的连接文本中出现；关键词之间为 AND，同一字段内为普通字面量子串匹配。
3. `locations`：每个计划地点至少命中 location.name 或 office.name 之一；多个地点为 OR。未提供地点时不筛选。
4. `departments`：每个计划部门按规范化名称与响应 departments.name 做字面量相等匹配；多个部门为 OR。
5. `offices`：每个计划办公室按规范化名称与响应 offices.name 做字面量相等匹配；多个办公室为 OR。
6. 每个筛选维度都必须满足；空维度不产生过滤条件。
7. 不使用正则、模糊相似度、词干化、同义词扩展、地理距离、LLM 或当前时间隐式过滤。
8. 缺失字段按“不命中”处理，不猜测、不从 HTML 或外部目录补齐。

过滤顺序必须固定并有纯函数测试：先关键词，再地点，再部门，再办公室；由于每个条件是纯布尔判断，最终集合应与顺序无关。测试需覆盖大小写、空白、中文、缺失字段、重复条件、无条件和空结果。

## 16. 排序、total 和内部分页

筛选后的所有岗位先排序，再计算 `total`，最后执行切片。默认排序为：

1. `updated_at` 按 `sort_order` 排序；缺失时间永远排在有值时间之后；
2. `title` 按 Unicode `casefold()` 后的值排序；
3. `board_token` 升序；
4. `id` 数值升序。

当 `sort_by` 为 `title`、`location` 或 `external_job_id` 时，将所选字段作为第一排序键，仍追加 `board_token`、`id` 作为不可省略的稳定 tie-breaker。`sort_order=desc` 只作用于主排序键；tie-breaker 保持升序，确保重复运行结果稳定。缺失可选值统一放在该主键的末尾。

分页语义：

- `total` 是本地筛选后、分页前的完整数量；
- `items = sorted_items[offset : offset + limit]`；
- `has_more` 按 `offset + len(items) < total` 计算；
- offset 超过 total 返回空 items 和 `has_more=false`，不是错误；
- 每次结果必须携带实际 `offset`、`limit`、`boards` 和 `fetched_count`，方便审计；
- 不向 Greenhouse 发送 `page`、`cursor`、`page_size` 或类似参数；不能将本地 `limit` 误称为远端 page size。

## 17. 无官方分页假设的处理

官方文档未明确提供或本任务未取得足够证据确认分页协议时，第一版必须整体获取官方列表：

- 只发送固定列表 GET，并读取完整、受大小上限保护的响应；
- `meta.total`（若存在）只能作为观测字段，不能触发第二次请求；
- 不猜测远端 `page` 从 0 或 1 开始，不猜测 cursor 字段、page size、Link header 或“默认第一页”；
- 不能因为本地 `limit=20` 就只获取 20 条；
- 响应过大直接失败并报告配置/数据问题，不静默截断；
- 后续只有在新的独立任务中引用最新 Greenhouse 官方文档确认分页字段、边界、排序和一致性语义后，才能扩展适配器。扩展必须新增契约、MockTransport 测试、错误语义和验收清单。

## 18. 去重、fingerprint 和持久化边界

T103 只做本次查询结果内的来源级去重，不做领域岗位合并：

- 去重键为 `(board_token, id)`；同一 board 同一岗位重复出现时保留第一次出现的完整记录；
- 不按 title、URL、公司、location、content 或 requisition_id 合并岗位；这些字段可能相同但不代表同一岗位；
- 多 board 中相同数值 `id` 视为不同记录；
- 去重发生在筛选和分页前，`fetched_count` 记录 Schema 校验后、去重前数量，`total` 记录去重筛选后的数量；
- 不计算 SHA-256、标准公司名、标准岗位名或任何 `fingerprint`；
- 不写 SQLite、缓存、磁盘快照或默认 `data/job_agent.db`；
- 不调用 `JobService`、Repository、事务或 ORM；
- 后续 T104 负责规范化、跨 URL/来源合并和 fingerprint，必须另有契约和测试。

## 19. Fake JobSource 与脱敏 Fixture

Fake 实现应位于 infrastructure，构造时显式接收已校验的 `JobSourceResult` 或不可变 `GreenhouseRawJob` 映射：

- 不扫描目录、不从环境变量读取真实 board、不创建 Client、不访问网络、不创建数据库；
- `search(plan)` 只在计划 board 有 Fixture 配置时返回确定性深拷贝；未配置 board 抛明确的 Fake 错误，不回显完整岗位内容；
- Fake 复用 SearchPlan 的本地筛选、排序和分页纯函数，或在测试中注入相同规则，避免另造语义；
- 每次返回独立对象，调用方修改结果不得污染下一次调用；
- Fixture 由测试显式通过 `Path(__file__)` 定位和加载，import 阶段不得读 JSON。

至少三份完全虚构的 JSON Fixture：

1. `jobs_normal.json`：两个以上合法岗位，含 location、department、office、content、updated_at 和稳定 id，覆盖正常筛选/排序/分页；
2. `jobs_empty.json`：`jobs: []` 的成功响应，覆盖空结果；
3. `jobs_invalid.json`：字段缺失、错误类型、非法 URL 或非 JSON 的错误样例；如拆成多个文件，至少覆盖 Schema 校验和非法 JSON 两种失败。

Fixture 禁止包含真实招聘资料、真实公司或真实岗位描述、个人信息、邮箱、手机号、密钥、Cookie、Token、Authorization、密码或可识别组织数据。建议统一使用 `example.com` 或其他明确保留的虚构域名，并在测试中断言敏感字面量不存在。

## 20. HTTP Client 生命周期

适配器必须明确 Client 所有权：

- 默认构造时不创建 Client；只有网络开关、计划和 allowlist 均通过后，首次 `search()` 才懒创建自有同步 `httpx.Client`；
- 测试可注入现成 Client 或 `httpx.MockTransport`，适配器不得关闭调用方拥有的 Client；
- 提供幂等 `close()` 和上下文管理器，关闭自有 Client；重复 close 不报错；
- Client 必须带显式 timeout、响应读取上限和必要的 Accept/User-Agent；不能使用无限 timeout；
- `search()` 发生异常时仍保留可安全关闭的生命周期状态，不把底层 Client/Response 放入 Port 返回值；
- import 阶段不得创建 Client、解析 Fixture、连接数据库或联网；
- 适配器不支持跨线程共享的隐式全局 Client。调用方负责实例生命周期和并发边界。

## 21. timeout、有限重试和错误分类

只对幂等 GET 的暂时性故障重试。默认最大尝试次数为 3（包括第一次），退避为固定 `[0.5, 1.0]` 秒，sleep 函数可注入测试；禁止无限重试、指数增长无上限或递归重试。

| 情况 | 是否重试 | 最终错误 |
| --- | --- | --- |
| 401、403 | 否 | `GreenhouseAuthenticationError` |
| 404 | 否 | `GreenhouseBoardNotFoundError` |
| 408 | 是 | `GreenhouseTimeoutError` 或 `GreenhouseRetriesExhaustedError` |
| 429 | 是 | `GreenhouseRateLimitedError` 或 `GreenhouseRetriesExhaustedError` |
| 500、502、503、504 | 是 | `GreenhouseServerError` 或 `GreenhouseRetriesExhaustedError` |
| 其他 4xx | 否 | `GreenhouseHTTPError` |
| 连接失败、DNS/传输错误 | 是 | `GreenhouseConnectionError` 或 `GreenhouseRetriesExhaustedError` |
| 客户端 timeout | 是 | `GreenhouseTimeoutError` 或 `GreenhouseRetriesExhaustedError` |
| 非法 JSON | 否 | `GreenhouseInvalidJSONError` |
| 响应超过最大字节数 | 否 | `GreenhouseResponseTooLargeError` |
| Schema 校验失败 | 否 | `GreenhouseSchemaValidationError` |

实施细则：

- 每次尝试、状态码、耗时和重试次数进入结构化观测，但不记录响应正文；
- 429 的 `Retry-After` 若未来支持，必须有上限并仍受最大尝试次数约束；T103 默认使用固定可注入退避，不假设 header 一定存在；
- 401/403/404 不因“可能暂时”重复请求；
- 重试耗尽后抛出包含 `board`、稳定错误码、attempts 和 trace_id 的安全异常，不回显 URL 查询、正文或认证信息；
- 一个 board 最终失败时，停止本次聚合并让整体 `search()` 失败；不得返回其他 board 的部分结果。

## 22. 空结果、整体失败和可观察性

### 空结果

所有请求成功、响应完整且记录合法，但本地筛选后无记录时：

- 返回成功的 `JobSourceResult(items=(), total=0, has_more=False)`；
- `fetched_count` 保留实际读取记录数；
- 记录 `outcome=empty`，不是 warning/error；
- 不返回默认岗位、旧缓存、示例 Fixture 或“未知岗位”。

### 整体失败

当任一计划 board 发生不可恢复错误或重试耗尽时：

- 整次查询失败，调用方收到明确异常；
- 不返回其他 board 的部分结果，不将失败 board 计为 0；
- 不自动使用上一次成功数据，除非未来任务明确设计带版本和用户确认的缓存；
- 错误必须能区分 board、HTTP 状态/错误分类、attempts 和 trace_id，但不能包含岗位全文、密钥、Cookie 或 Authorization。

### 可观察性

至少记录结构化事件：

```text
event_name=job_source_search
source=greenhouse_job_board
trace_id
boards_count
board_token_hash_or_redacted_id
plan_hash
attempts
fetched_count
filtered_count
returned_count
duration_ms
outcome=success|empty|error
error_code
```

日志中禁止记录完整 `content`、absolute_url 查询秘密、原始 JSON、Authorization、API Key、Cookie、个人信息或完整 SearchPlan 文本。board token 是否可明文记录必须由部署安全策略决定，默认使用稳定哈希或脱敏值。

## 23. 默认离线和网络触发边界

默认离线是硬约束：

- import、构造、契约校验、Fake、普通单元测试和 `python -m job_agent` 都不联网；
- 只有同时满足“网络开关显式为真、配置合法、计划合法、每个 board 在 allowlist、调用方明确执行 `search()`”时才发出 GET；
- 仅创建 Greenhouse 适配器不联网；仅构造 `SearchPlan` 不联网；
- 非法计划和 allowlist 拒绝必须发生在第一个网络请求前；
- 不从用户输入直接启用网络，不把“有 board token”视作同意联网；
- live smoke 如保留，必须显式 pytest marker/环境变量 opt-in，默认跳过，使用获得组织授权且在 allowlist 的 board；
- 测试进程应通过 MockTransport 证明没有真实网络连接，必要时 monkeypatch socket/transport 使误用直接失败。

## 24. 安全、隐私与合规

Greenhouse 官方 API 能力与组织使用权限必须区分：

1. **官方技术能力**：Greenhouse Job Board API 文档公开描述了通过 `boards-api.greenhouse.io` 对指定 board token 执行 GET 列表/岗位读取的技术接口；这是“接口可以如何调用”的事实，不等于任何组织、任何 board 都自动允许任意使用。
2. **组织权限和数据责任**：使用组织必须自行确认目标招聘板的数据访问、使用、保存、内部共享和再分发权限，以及适用的合同、隐私政策、条款、速率限制和组织授权。board token 在 allowlist 中只代表本系统配置层允许访问，不证明法律或合同授权。
3. **本规格不是法律意见**：合规判断、数据保留期限、跨境传输、再分发和个人信息处理必须由使用组织及其法务/隐私负责人确认。
4. **访问边界**：只访问显式 allowlist 中的 board；不自动发现或枚举 board，不抓取 HTML，不绕过认证、robots、访问限制或反自动化措施。
5. **最小数据原则**：只保留实现搜索和后续用户确认所需的岗位字段；不收集候选人 Profile、简历、Cookie、密码或投递数据；不向 Greenhouse 发送这些信息。
6. **日志和错误脱敏**：API URL、响应、岗位正文、个人数据和凭据不得进入普通日志、异常文本、Fixture 或 Git。
7. **保存和再分发**：T103 不持久化来源结果，也不向第三方再分发；未来如需缓存、导出或展示，必须单独评估授权、保留期限、删除和审计。

官方参考（实施时应重新核验版本和条款正文）：

- [Greenhouse Job Board API 官方文档](https://developers.greenhouse.io/job-board.html)
- [Greenhouse 官方 Terms of Service](https://www.greenhouse.com/terms-of-service)

### Greenhouse MockTransport 测试

使用 `httpx.MockTransport` 或等价离线传输，并断言请求方法、官方 API host、path、唯一 `content=true` 参数和无 Authorization：

- 一个 board 失败：断言整体失败且不返回其他 board 部分结果；

- Client close：自有 Client 关闭、注入 Client 不关闭、重复 close 幂等；
