# 数据库与持久化

## 1. 持久化边界

系统存在三类持久化：

1. **业务数据库**：保存候选人、岗位、匹配、材料、投递和事件；
2. **LangGraph Checkpoint**：保存工作流执行状态和中断恢复信息；
3. **文件存储**：保存原始简历、生成简历、截图和投递快照。

三者不得混用。业务事实不能只存在 Checkpoint 中；Cookie 和 PDF 字节不写进普通业务表。

## 2. 数据库选型

- MVP：SQLite；
- 正式或多进程：PostgreSQL；
- ORM：SQLAlchemy 2.x 风格；
- 迁移：Alembic；
- Repository 屏蔽数据库实现差异。

### 3.3 resume_evidence

| 字段 | 类型 | 约束 |

### 3.4 jobs

至少包含：`id`、`external_job_id`、`company`、`title`、`location`、`url`、`source`、`raw_jd`、`normalized_json`、`fingerprint`、`deadline`、`discovered_at`。

约束：`fingerprint` 建唯一索引；重复来源写入来源关联或更新已有记录。

### 3.5 job_matches

至少包含：`id`、`candidate_id`、`job_id`、`hard_filter_passed`、`overall_score`、`details_json`、`created_at`。

建议 `(candidate_id, job_id)` 唯一；重新评分时更新当前结果，并按需要保留历史版本表。

### 3.6 resume_versions

至少包含：`id`、`candidate_id`、`job_id`、`base_resume_id`、`content_json`、`source_evidence_ids_json`、`file_path`、`content_hash`、`created_at`。

### 3.7 applications

至少包含：`id`、`candidate_id`、`job_id`、`status`、`application_url`、`resume_version_id`、`submitted_at`、`last_updated_at`。

建议 `(candidate_id, job_id)` 建唯一约束，防止重复投递记录。

### 3.8 application_answers

保存问题、答案、问题类型、字数限制、证据 ID 和用户是否修改。

### 3.9 application_events

事件只追加，不覆盖。保存事件类型、前后状态、来源、详细信息和时间。

### 3.10 browser_runs

保存 Application Adapter、阶段、成功状态、错误代码、截图路径和运行时间；不得保存 Cookie 或密码。

## 4. Repository 接口

Repository 只负责持久化，不做 LLM 调用和业务编排。

```python
from typing import Protocol


class JobRepository(Protocol):
    def get(self, job_id: str): ...
    def get_by_fingerprint(self, fingerprint: str): ...
    def upsert(self, job): ...
    def list_for_candidate(self, candidate_id: str, *, limit: int = 100): ...


class ApplicationRepository(Protocol):
    def get(self, application_id: str): ...
    def get_by_candidate_and_job(self, candidate_id: str, job_id: str): ...
    def create(self, application): ...
    def update_status(self, application_id: str, status): ...
    def append_event(self, event): ...
```

Repository 返回领域 Schema 或明确 DTO，不返回裸 ORM 实例给 UI。

## 5. 事务边界

- 创建 Application 和首个 Event 在同一事务中；
- 更新状态和追加状态 Event 在同一事务中；
- 保存 ResumeVersion 的元数据和文件写入采用“先临时文件、后原子改名、再提交数据库”或补偿机制；
- 外部网页提交不能与数据库构成单一事务，因此通过幂等键、提交前后截图和事件补偿。

## 6. 幂等性

关键幂等键：

- 岗位：`fingerprint`；
- 投递：`candidate_id + job_id`；
- Graph：`application-{application_id}`；
- 浏览器提交尝试：`application_id + submission_attempt_no`；
- 快照：`application_id + snapshot_stage`。

任何重试都先查询现有记录，不直接重复插入。

## 7. Checkpoint

开发环境使用 SQLite Checkpointer。正式多进程环境使用 Postgres Checkpointer。

`thread_id` 约定：

```text
profile-<candidate_id>
discovery-<run_id>
application-<application_id>
tracking-<run_id>
```

Checkpoint 中引用业务对象 ID，而不是复制全部业务事实。

## 8. 文件与快照

```text
data/
├── resumes/original/
├── resumes/generated/
├── snapshots/<application_id>/
├── browser/screenshots/
└── auth/
```

每次正式提交至少保存：

```text
job.json
match_result.json
application.json
answers.json
resume.pdf
before_submit.png
after_submit.png
manifest.json
```

`manifest.json` 保存文件 SHA-256、URL、Adapter 版本、审批信息、时间和结果。

## 9. 数据删除与保留

- 支持按候选人导出业务数据；
- 删除 Candidate 前明确列出级联影响；
- 默认不自动删除投递审计信息；
- 认证状态允许独立清除；
- 测试 Fixture 必须脱敏，不复制真实身份证、Cookie 或 Token。
